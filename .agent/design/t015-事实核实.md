# T015 规划依赖的仓库外事实：站主的核实（2026-10-23）

规划报告：`.agent/mailbox/tasks/T015-1-plan/report.md`（本机信箱，不提交）。下面是站主在本机实测的结果（Bun 1.4.2、Node 24、Windows Server 2025），合同端照此写合同。实验脚本在站主会话的草稿目录里，结果原样记在这里。

【一、事实】
F1 Bun 版本：已核实。`bun --version` 是 1.4.2，装好戳记里的 bun_path 也是它。合同按 1.4.2 的行为写。

F2 req.url 是否保留原始路径：实情相反，交给 fetch 的 req.url 是规范化过的。
- 原始请求行 `GET /a/../b/%2e%2e/%2fx\y?q=1`，fetch 收到的是 `http://127.0.0.1/%2fx/y?q=1`：
  - `..` 与 `%2e%2e` 已按 WHATWG URL 的规则解析掉；
  - 反斜杠换成了 `/`；
  - 只有 `%2f` 保留编码。
- 合同据此写三点：
  1. 经 HTTP 的 T13 负面测试断言“拿不到 --assets 之外的文件”（回 404，或落在 assets 之内规范化后的路径上），不断言“服务看到了原始的 `..` 并拒绝”。
  2. 静态资源的路径解析写成纯函数，照样拒绝各种原始形式：`..`、`%2e`、`%2f`、`%5c`、反斜杠、盘符、UNC、含 `:` 的名字、末尾带点或空格的段。这是纵深防御，由纯函数测试逐类覆盖。
  3. 编码过的分隔符（`%2f`、`%5c`）到得了 fetch，HTTP 层必须拒绝，配 HTTP 负面测试。

F3 Bun 自己拒掉的请求：部分属实，分三种：
- Content-Length 超过 maxRequestBodySize：不调用 fetch，Bun 自己回 413，没有安全头。
- 畸形请求行（`GARBAGE`）：不调用 fetch，Bun 回 400（只有 Connection: close），没有安全头。
- 分块传输、正文超过 maxRequestBodySize：fetch 会被调用，但正文读到超限时，Bun 自己回 413（没有安全头），处理函数里 catch 给出的响应没有发出去。
- 所以服务自己的计数（64 KiB 加 1 就停）必须先于 Bun 的上限触发；规划定的 2 倍是对的。分块传输的负面测试断言的是服务给的 413（带安全头）。

F4 server.stop(true)：已核实。保活连接 3 毫秒内被关掉；不带 true 的 stop() 也关掉了空闲的保活连接。
- 注意：客户端和 Bun.serve 在同一个 Bun 进程里时，node:net 客户端收不到 close 事件（实测三项都等到超时）。测试的客户端放在 Node 一侧，服务在单独的 Bun 进程里（Vitest 本来就跑在 Node 上）。

F5 Date 与 HEAD：部分属实。
- GET 的响应 Bun 会自动加 Date（还有 content-type、Content-Length）。
- HEAD 会交给 fetch（req.method 是 "HEAD"），但 HEAD 的响应里没有 Date。
- 测试不要依赖 Date。
- 站主决定：照 D4“只有 GET 与 POST”，HEAD 与其他方法一律回 405，带安全头。

F6 stdin 在 Windows 管道上的 EOF：已核实。Bun 1.4.2 下 process.stdin 是管道时，写端一关，`for await` 就结束。直接起，和经一层 Python 起（subprocess.run 原样继承 stdin，与 run_handoff 相同），两种都在 0.5 秒内退出 0。

F7 每条连接的空闲超时：实测约 10 秒。一条空闲的保活连接在连上 12 秒后被服务端关掉，含先等的 0.5 秒与计时粒度。Bun 文档的默认值是 10 秒，可以用 Bun.serve 的 idleTimeout 设，上限 255。服务的空闲退出（1800 秒）与它无关。

F7b（2026-10-24，T017 规划时补，规划端实测，Bun 1.4.2，客户端在 Node 一侧）服务端往外写数据**不会**重置这个空闲计时：idleTimeout 设 2，SSE 流每 500 毫秒写一行心跳，客户端收到 7 次心跳，连接照样在 4.0 秒被断开，与一个字也不写的流（3.98 秒）一样。只给某一条请求关掉空闲超时可以用 `server.timeout(req, 0)`（fetch 的第二个参数就是 server）：同样条件下 8 秒不断、收到 15 次心跳。SSE 因此不能靠心跳保活，要对订阅请求调 `server.timeout(req, 0)`；全局的 idleTimeout 不用改。探针在规划端会话的 scratchpad（sse-probe/server.ts、client.mjs）。

F8 Node 下 lstat 认不认得出 junction：已核实。Node 24 与 Bun 1.4.2 下，lstat 一个 junction 都是 isSymbolicLink() 为 true、isDirectory() 为 false；stat 跟随之后是目录；readdir 的 withFileTypes 条目 isSymbolicLink() 也是 true。

F9 Electron 主进程发请求带不带 Origin：未核实，本机没有 Electron。本片不依赖它：照规划的 controlOriginAllowed（没有 Origin 或同源都接受；别的站点 403，不计入限速），两种情况都成立。D3 外壳实现时实测，记进 §5.1。

内核清单里另外三条：
- node:http 客户端能自定义 Host 头：已核实，服务端收到的是 `evil.example:<port>`。
- Vitest 2.1.8 的 vi.mock 能包住 node:crypto：已核实。被测模块里 `import { randomBytes, timingSafeEqual } from "node:crypto"` 的具名导入被换掉了，调用次数也能断言。
- fs.symlinkSync(target, path, 'junction') 不要管理员权限：本会话与执行端都以管理员身份运行，这里没法实测非管理员的情形。Windows 的目录联接本来就不需要 SeCreateSymbolicLinkPrivilege（与符号链接不同），本机测试照样能建 junction，合同不另写非管理员的分支。
