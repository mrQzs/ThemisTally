# 返工（REVISE）规则

默认预算是一次初始执行加一次定点返工（`max_attempts_total: 2`，按 task-id 汇总所有版本）。

## 一、先分类，再计数

结论是 REVISE，不等于马上再派遣一次。先判断差异来自哪里：

| 来源 | 判断依据 | 处理 |
|---|---|---|
| 合同缺陷（PLAN_ERROR） | 接口或事实写错，验收项矛盾，行为没有定义 | 规划器修订合同，出新版本；不计入执行失败 |
| 执行偏差（EXECUTION_ERROR） | 合同清楚，但实现漏了边界或写错 | 定点返工 |
| 环境问题（INFRA_FAILURE） | 依赖、服务或凭据问题 | 先修环境，不改合同 |
| 能力不足 | 同一验收项在清楚的合同下重复失败 | 拆得更小；由规划器实现难点；或经用户同意更换执行模型（写入新合同与 environment.md） |

同一验收项失败两次后，不要再原样派遣。

## 二、新版本合同写什么

新版本（vN+1）的输入必须包括：

- 上一轮复审报告中“需要修正的具体差异”：文件、行为、失败的检查 ID 与关键输出（截取相关的几行，不要附整份日志）；
- 选定的基线策略（见下）；
- 剩余预算：`bash scripts/dispatch-pi.sh status <task-id>` 显示已用次数与时长。

Steps 只写需要修正的内容与验证方法。不要写“再试一次”或“修复所有问题”。

## 三、基线策略（二选一，写进合同）

1. **在上一轮候选上继续**：适合大部分实现正确、只差局部修正的情况。
   - 运行 `bash scripts/dispatch-pi.sh branch <上一轮 run-dir> --rework`。它会基于候选树创建一个提交，以及 `pi-rework/…` 本地分支。
   - 把输出的提交 ID 设为新合同的 `base_sha`。
   - Repository facts 注明：“基线包含上一轮候选（attempt NNN）”。
2. **从原基线重做**：适合方向错误，或候选混入了越界修改的情况。
   - `base_sha` 保持原值，在合同中写明“放弃 attempt NNN 的实现”。

两种策略不要混用在同一个合同里。

## 四、预算用完时

`prepare` 报 `BUDGET_EXCEEDED` 时，不要改大预算绕过。向用户说明已用次数、失败分类与建议（拆小、换人实现、换模型），由用户决定是否追加预算。追加的预算要写进新版本合同。
