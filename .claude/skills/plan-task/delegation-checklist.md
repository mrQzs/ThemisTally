# 委派判断与任务拆分

## 一、是否值得委派

任务同时满足以下五条时适合交给 Pi：

1. **清晰**：目标、范围与行为都能写成合同，不需要执行器做设计决定。
2. **可独立验证**：至少有一条能在 worktree 中自动运行的检查（校验器要求），其余要点可以列为人工复审点。
3. **边界稳定**：涉及的接口在执行期间不会被其他工作改动。
4. **失败易恢复**：候选不合格时，丢弃 worktree 即可，不会留下外部副作用。
5. **划算**：预计节省的执行成本能覆盖规划、派遣与复审的协调成本。

**不值得委派**时，直接完成或先调查：

- 一处文案或几行显而易见的修正。协调成本高于直接完成。不要用“单文件少于 30 行”作硬阈值：一行权限判断也可能风险很高。
- 根因未明的缺陷：先调查到能写出修复方案为止。
- 需要架构取舍、认证授权语义、生产数据迁移的决定：先由规划器或人确定设计，再看能否拆出可委派的部分。
- 需要远程写入、生产凭据或不可逆外部副作用的任务。

**优先委派**：补充输入校验、实现已定义的接口、局部修复、补回归测试、按确定规则重构、机械的跨文件改名。

## 二、输入包只放决定执行所需的信息

合同里应该有：目标、事实、已选设计、允许范围、涉及的接口、相关源码入口、检查命令、失败时的行为，以及必要的既有约束。

不要默认附上整段聊天、整个仓库、全部测试日志或无关的设计历史。

精简上下文时不能删掉重要限制。例如精简认证代码时，不能省略会话代次、取消请求和刷新令牌轮换规则。

给出既有helper供复用前，核对接受基线中的实际导出名；计划在调用方使用的别名不等于模块已有该符号。任务比通用AGENTS更严格的执行限制应放在Scope/Forbidden中显眼写明，避免只埋在长示例后的检查说明里；这是明确限制的位置，不自动改变已有授权。

## 三、按可验收的结果拆分

| 不理想的任务 | 更好的拆分 |
|---|---|
| 优化整个鉴权模块 | 明确刷新语义 → 实现刷新协调器 → 接入请求重放 → 回归验证 |
| 整理所有配置 | 定义配置映射 → 修改一个配置域 → 验证兼容读取 |
| 修好测试 | 定位失败原因 → 修复指定缺陷 → 复测对应测试集 |
| 把 X 迁移到新 API | 列出调用点 → 每批 N 个调用点一个任务 → 删除旧 API（最后一个任务） |

- 每个子任务只有一个主要结果，依赖关系清楚。
- 不要为了少传上下文，把相互依赖的修改拆成无法单独验证的碎片。
- 拆分后先派遣最底层的任务。上层任务的合同等下层任务被接受（PASS 并集成）后再写，base_sha 用下层任务集成后的提交。

### 按实际执行反馈控制大小

- 冻结前分别估算调查、实现、补测、运行必要检查和最终报告；不能把全部时限都算成编码时间。已有相近任务用满时限或漏掉多类边界时，下一份未派遣任务应缩小到一个可独立验收的结果。
- 不以文件数或合同字数设硬阈值。一份测试文件同时验证权限、解析、映射、摘要和兼容，可能比多个机械文件修改更难。
- 源码已正确但测试无效时，返工只补证据。产品缺陷和测试缺口分开列，避免重做已通过部分。
- 已开始任务继续沿用同一 task-id 计数，不用拆名重置预算。尚未派遣的任务可以调整拆分，但必须同步依赖与原需求的归属，不能丢验收项。
- 记录规划与复审耗时、返工原因和残余缺口；执行器 token 数或全绿测试数不能单独说明委派划算。

## 四、并行条件

同时满足以下条件才并行：

- 接口已经稳定；
- 各任务的修改范围基本不重叠；
- 基线明确。

每个任务使用自己的 attempt 与 worktree，调度器会自动分开。

任务 B 依赖任务 A 的实现时，B 从 A 已接受的提交开始，不要让两个执行器同时猜同一个接口。

所有并行任务集成后，还要在组合结果上运行受影响的检查，不能把各自 worktree 中的绿色结果直接相加。
