## 一、结论

方案的主线是对的，值得落地：

- 高能力模型规划与验收，Pi 执行；
- 合同落盘、证据优先、有限重试；
- 按整个任务核算成本。

需要修正的主要是落地时的细节，集中在四类：

1. **Pi 会静默接受几类错误输入**：思考级别写错、工具名写错、模型 ID 写错时，只警告或直接忽略，不报错。
2. **附录 A 的脚本不够稳妥**：可能卡在 stdin 上；在 Windows 和从 Claude Code 调用时不可靠；没有把证据绑定到确切的候选内容。
3. **执行器可以写到 worktree 之外**，而方案的收集方式发现不了。
4. **状态、结论与失败分类的命名前后不一致**，状态机有没有出口的状态。

`claude-pi-kit/` 针对这些问题给出了处理方式，之后又经 OpenAI Codex 独立审查，按第八节修订过一轮：

- 4 个 Skill 与配套文档；
- 调度工具 `scripts/pi_dispatch.py` 及其自测 `tests/test_dispatch.py`：修订后 91 项端到端断言在本机用模拟的 Pi 全部通过，并用真实 pi 0.87.0 做了不调用模型的衔接验证；
- 执行模型按你的要求改为 Step、思考级别 `high`。

## 三、需要修正的问题

### 高：会导致挂起、误判或越权却发现不了

**H1. Pi 可能卡在 stdin 上**

- **现象**：stdin 不是终端时，Pi 在 print / json 模式下会一直读到 EOF，读到的内容会拼接进第一条提示词（见源码 `readPipedStdin`）。附录 A 没有重定向 stdin。从 Claude Code、CI 或其他工具以管道方式启动时，可能一直挂到 `timeout` 触发才结束。
- **处理**：调度工具启动 Pi 时，把 stdin 固定为空设备。

**H2. Pi 会静默接受错误输入**

- **现象**：
  - 思考级别无效时只打印警告，然后忽略；
  - `--tools` 中的未知工具名会被静默丢弃（源码注释如此，未实测）；
  - provider 已知但模型 ID 写错时，按自定义 ID 照发请求。
  附录 A 只检查参数名是否存在，这三种错误都不会被拦住。
- **处理**：
  - 运行前预检：核对思考级别与内置工具名，用 `pi --list-models` 精确匹配模型，运行 `pi auth check`；
  - 运行后：扫描 stderr 中的相关警告，并核对每条 assistant 消息的 provider / model 与 `providerThinkingLevel`。

**H3. 规划器如何等待执行，方案没有说明**

- **现象**：Claude Code 的前台 Bash 命令默认最长 10 分钟，可用 `BASH_MAX_TIMEOUT_MS` 调整，超时的命令会被转到后台。方案默认单轮时限是 1200 秒。
- **处理**：`/dispatch-pi` 明确要求用 `run_in_background` 运行，等完成通知，不用 sleep 轮询。非交互模式（`claude -p`）下，后台命令会随会话结束而终止，另作说明。

**H4. 执行器可以写到 worktree 之外**

- **现象**：
  - Pi 的工具以用户权限运行，可以用绝对路径修改主工作区或其他目录，worktree 的 diff 看不到这些改动；
  - 附录 A 还让执行器把 `REPORT.md` 直接写进主仓库的证据目录。
- **处理**：
  - 执行报告改为从最后一条 assistant 消息中提取，执行器不再需要写证据目录；
  - 记录工具访问过的 worktree 之外的路径；
  - 比较运行前后主工作区的 HEAD 与内容快照（已跟踪与未被忽略文件的内容）。第一版只比较 `git status` 的输出，发现不了对已有脏文件的再次修改，经 Codex 指出后更正（第八节第 12 条）。

**H5. 候选内容没有被固定**

- **现象**：附录 A 只收集已跟踪文件的 diff 与未跟踪文件的路径清单，新增文件的内容没有保存，也没有候选摘要。§15.1 要求的“验收绑定确切内容”无法实现。
- **处理**：
  - 用临时索引记录候选树 ID（包含未被忽略的新文件），不改动 worktree 的索引与 HEAD；
  - 保存完整的二进制补丁，并在基线上重放一次，确认得到同一棵树（往返校验）；
  - `check`、`verdict`、`branch` 都绑定到这个树 ID。

**H6. 在 Windows 上不可用**

- **现象**：
  - 本机的 `python3` 是应用商店的占位程序，附录 A 的哈希步骤依赖它，会直接失败；
  - npm 安装的 `pi` 是 `.cmd` 包装，参数会经过 cmd.exe 解析，中文与特殊字符有风险。
  方案只写了“Windows 建议先在 WSL 运行”，而本机没有安装 WSL。
- **处理**：
  - 调度逻辑用 Python 重写，只依赖标准库；
  - 绕过 `.cmd` 包装，直接用 node 运行入口脚本；
  - `dispatch-pi.sh` 会跳过无法运行的 python 占位程序；
  - 在 Windows 上用 Job Object 管理 Pi 的整个进程树。已实测两种情况：超时时会回收孙进程；调度器进程本身被强制结束时，Pi 与孙进程也会一并被回收，不会留下无人监督、继续计费的执行器。
- 附注：本机实测 Git Bash 自带的 `timeout` 在简单场景下也能结束孙进程，所以进程回收不是附录 A 在 Windows 上的主要问题。

### 中

**M1. 规则文件的实际加载方式**

- Pi 在每个目录只读取第一个存在的文件，顺序为 `AGENTS.override.md` → `AGENTS.md` → `CLAUDE.md`。同一目录两者都有时，Pi **不读** CLAUDE.md。
- Claude Code（2.1.277 及以后）只在没有任何 CLAUDE.md 时才读取 AGENTS.md。
- 所以 §10.3 / §10.4 担心的“两端读到同一份规则”，实际取决于是否导入。套件的做法是：CLAUDE.md 用 `@AGENTS.md` 导入共享规则，AGENTS.md 中的执行器规则按角色书写。

**M2. worktree 从基线提交创建**

未提交的 AGENTS.md 不会出现在执行器的工作副本里，方案没有提示这一点。现在 `validate` 与 `doctor` 都会检查。

**M3. worktree 位置改变了 Pi 的上下文来源**

- worktree 位于系统临时目录时，Pi 会沿 worktree 的祖先目录向上加载上下文文件（例如用户主目录下的 AGENTS.md），另外还会加载 `~/.pi/agent` 下的 AGENTS.md 与 SYSTEM.md。这条祖先链与主仓库的不同。
- 调度工具会把实际会加载的文件及其哈希记入 `preflight/context-files.json`。

**M4. 状态、结论与分类的命名不统一**

- 方案中混用了四套名称：
  - 脚本状态：PREPARED / NEEDS_REVIEW / EXECUTION_STOPPED；
  - 状态机：DRAFT / READY / VERIFYING；
  - 结论：PASS / REVISE / BLOCKED / ESCALATE；
  - 门禁输出：INFRA_FAILURE、ACCEPTED_WITH_EXCEPTION。
- §12.1 的状态机中，TIMEOUT、INFRA_FAILURE、ESCALATE 没有出边，也缺少 CANCELLED 与 BUDGET_EXCEEDED。
- 套件在 `review-pi/gates.md` 中统一为：attempt 状态表、五种结论、八种失败分类。

**M5. 预算没有强制执行**

- 附录 A 不强制总次数与累计时长，方案已承认这一点；“一次初始执行加一次定点返工”只能靠人记住。
- 调度工具现在按 task-id 汇总并强制执行，预检失败的 attempt 不计次数。预算核算与领取在 task 级锁内完成，同一 task 的两个 attempt 不能同时用掉最后一次额度（第八节第 4 条）。

**M6. 缺少数据外发的授权**

- 派遣会把合同与代码发给执行模型的提供商，方案的 `authorized_actions` 没有覆盖这个动作。
- 现在由 `/dispatch-pi` 把关：用户必须在对话中明确要求执行。合同中也把“执行器授权”和“集成授权”分开。

**M7. 凭据对执行器可见**

- Pi 的 shell 工具会继承环境变量。§5.4 讲了凭据最小化，但没有提到环境继承。
- 调度工具默认移除推送、发布类凭据（GITHUB_TOKEN、NPM_TOKEN、SSH_AUTH_SOCK 等），并说明这不是隔离措施：模型提供商自己的 API key 必然对执行器可见。

**M8. 测试产物被误判为候选内容**（本次测试中发现）

- 测试生成的 `__pycache__` 会被当作新文件，进而被判为候选漂移。
- 第一版把所有新增文件都当作无害。Codex 指出（第八节第 1 条），这会让一个依赖复审者补上的文件的候选通过验收，已收紧为：
  - 只放行缓存类文件：默认是 Python 缓存，其他可配置；
  - 检查前出现其他新文件，`check` 拒绝运行；检查自己产生的新文件，让 G4 失败；
  - 另提供 `check --fresh`，在干净副本上验收；
  - 默认设置 `PYTHONDONTWRITEBYTECODE=1`。

**M9. 用量统计的口径**

见第二节第 12 条。调度工具按修正后的口径汇总，费用标为 estimated、partial 或 unknown，缺失时不写成 0。

**M10. 执行期可能产生网络下载**

本机 PATH 与 `~/.pi/agent/bin` 中都没有 rg / fd 时，Pi 的 grep、find 工具首次使用会从 GitHub 下载它们（设置 `PI_OFFLINE` 时除外）。`doctor` 会提示这种情况；本机 `~/.pi/agent/bin` 中已有这两个工具。

### 低

**L1.** 附录 A 的 attempt 目录名是随机的（attempt-XXXXXXXX），不满足 §12.4 中 attempt 编号的要求。现在改为按任务顺序编号 `attempt-NNN`，并用原子性的 mkdir 分配。

**L2.** §6.4 要求 Markdown 与 JSON 合同保持一致，但没有实现。现在由 `validate` 检查：章节、Identity（版本、基线、风险、授权、执行模型与思考级别）、路径、依赖策略、预算数值、每个检查的命令参数、DoD ID、占位符。其中与执行相关的比较是按第八节第 5 条加强的。执行说明还附有由 JSON 生成的“机器合同摘要”。

**L3.** §6.3 的 `authorized_actions` 没有给出取值范围；§6.4 的 JSON 缺少 risk_level、执行器配置、setup、DoD 与证据的映射、输出匹配等字段。现在在 `contract-guide.md` 中定义。

**L4.** §8.2 的 `--tools` 写法是正确的（grep、find、ls 默认关闭）。补充：Windows 上可以用内置的 `powershell` 工具。

**L5.** `pi --help` 中 `--provider (default: google)` 的说法有误导。没有指定模型时，默认模型实际上按已保存的设置或已有凭据的 provider 顺序选择。所以合同必须同时给出 provider 与精确的 model。

**L6.** Skill 被调用后，在上下文压缩时只会重新附加前 5000 token（多个 Skill 合计 25000）。官方也建议 SKILL.md 不超过 500 行。方案中的 Skill 模板把全部内容写在一个文件里；套件把细节拆到附属文件，四个 SKILL.md 正文各约 1000–1200 token。

**L7.** 附录 A 直接用 pi 的退出码作为脚本退出码，超时（124）、SIGTERM（143）与业务失败混在一起。调度工具的退出码只表示调度结果：0、1、2、3、4 各有固定含义。

**L8.** §10.2 建议“对固定命令配置窄规则”，但没有给出示例。套件提供了 `.claude/settings.example.json`：预授权只读子命令，并禁止 Claude 编辑 `.agent/runs/`。

## 四、按你的要求所做的调整：Step 模型用 high

- 合同模板、两个示例、调度工具的默认值（原方案为 `low`）、允许列表示例与环境模板，都统一为 `thinking: high`。
- **本机核验结果**（只读取了非敏感字段，没有读取或输出 apiKey，没有调用模型）：
  - 自定义 provider `step`，定义在 `~/.pi/agent/models.json`，使用阶跃星辰的 `step_plan` 端点与 anthropic-messages 协议；
  - 模型 `step-5-preview`，`reasoning: true`，`thinkingLevelMap: {"max": "max"}`；
  - `pi --list-models step` 能列出它，`pi auth check` 结果为 ready。
- **按 Pi 源码的规则**，这个模型支持 off / minimal / low / medium / high / max，不支持 xhigh，所以 Pi 会接受 `high`。
- **实际发送形式由协议决定**（第一版写成“原样发送”，是错的，经 Codex 指出后按源码更正）：
  - 本机 `step` 使用 anthropic-messages 协议，没有开启 adaptive thinking，Pi 走预算模式：high 对应 `thinking.budget_tokens = 16384`（minimal 1024、low 2048、medium 8192；这种模式下 xhigh 与 max 也按 high 的预算发送），可以在 Pi 的 settings 中用 `thinkingBudgets` 调整；
  - 这种配置下，assistant 消息不带 `providerThinkingLevel`，只能确认请求的级别，无法证明服务端实际按 high 推理。
- 套件的示例与允许列表因此使用 `step/step-5-preview`。另外记录了 Pi 内置目录中的 Step 3.7 Flash（openrouter、vercel-ai-gateway、huggingface），它只支持 low / medium / high。
- **请确认**：本机 `step-5-preview` 的 `contextWindow` 是 10,000,001,000,000，`maxTokens` 是 1,000,000，看起来像笔误。Pi 按 contextWindow 判断何时自动压缩上下文，这个值会让自动压缩几乎不触发。建议按阶跃星辰的文档填写实际数值。本次没有修改这个文件。
