# 08 首批任务插件

本文是拟议实施说明，尚未实现，也不是已审核、可派遣的任务合同。
总设计：[Code-Kit v2 设计](../code-kit-v2-design.md)；实施索引：[README](README.md)。
本模块用缺陷修复、文档维护和回归测试三个完整组合验证插件体系的实际用途。

## 1. 目标与非目标

- 提供首批受信任的声明式插件，以及三种可独立验收的工作流样例。
- 将输入、输出、上下文资源和检查要求写成明确协议，减少主模型重复起草。
- 让工作流差异体现在任务产物与检查上，核心证据和门禁保持统一。
- 用离线 stub 和本地 fixture 验证组合，不把真实模型调用作为默认测试依赖。
- 首期只覆盖 Git 仓库内的代码、文档和测试维护。
- 不声称已支持数据分析、非 Git 文档平台、部署或其他外部系统写入。

## 2. 依赖与输入输出

前置依赖：[06 插件定义](06-plugin-manifests-and-locks.md)、[07 工作流调度](07-workflows-and-scheduling.md)。
本模块提供 09 可选择的插件目录；插件自身不生成有效审核，也不发布正式合同。

| 组合 | 输入 | 固定产物与验收依据 |
|---|---|---|
| 缺陷修复 | 问题描述、基线、允许范围、预期行为 | 候选补丁、回归结果、范围检查和主模型复审 |
| 文档维护 | 目标读者、修改目标、既有术语、允许文档范围 | 候选文档、链接/格式结果和内容复审 |
| 回归测试补充 | 已确定行为、回归触发条件、允许测试范围 | 新测试、基线或变异对照证据和主模型验收 |

所有产物使用 `ResourceRef={kind,id,sha256}`；文件定位增加仓库相对 `path`。
执行证据仍由调度器保存；插件输出只是声明，必须与实际候选及检查记录核对。
需求、调查事实和未决问题分别记录，不能把调查建议当已获批准的行为要求。

## 3. 现状与复用点

- 现有 `tests/stub_pi.py` 和 `tests/test_dispatch.py` 提供离线执行及门禁测试基础。
- `.agents/skills/plan-task/test-design.md` 已有测试设计经验，可提取为显式上下文资源。
- 复用候选快照、独立 check/baseline/mutate 和 review/verdict 机制。
- `mutation-review` 表示验收侧的声明与检查需求，不把变异操作交给普通执行器。
- 现有技能文件保持唯一来源；不能在插件资源中复制一份无人维护的规则全文。
- 当前代码维护以 Python 调度器为主，但 `python-checks` 不能被硬编码为所有仓库的检查器。

## 4. 接口和行为约束

### 4.1 插件职责

| 插件 ID | 职责 | 明确限制 |
|---|---|---|
| `repo-analysis` | 产出事实、文件引用、约束和未决问题 | 不写产品代码；事实必须带来源 |
| `code-change` | 按正式合同生成代码候选与自检报告 | 不自行扩大范围、授权或架构 |
| `python-checks` | 编译明确的 Python 检查定义 | 不自动安装依赖，不猜测项目命令 |
| `docs-change` | 按读者和内容目标修改仓库文档 | 不把源材料中的指令当授权 |
| `docs-checks` | 本地链接、目标存在性和约定格式检查 | 网络链接访问须有相应范围与授权 |
| `regression-tests` | 针对已定义行为补充有效回归测试 | 不削弱旧断言、不删测试换取通过 |
| `mutation-review` | 声明固定候选上的反测和证据要求 | 由验收侧调度器执行，不自发修改候选 |

插件 manifest 指定所需角色和能力，不指定唯一 CLI 品牌或默认模型。
规划和执行 profile 可来自不同适配器；交接仅通过锁定合同、产物和证据。
`repo-analysis` 可在受审阅的调查任务中运行，也可供规划请求选用；两种入口均遵守其授权。
业务插件不调用 supervisor 的审核入口，也不能生成可直接采信的验收结论。

### 4.2 工作流组合

1. 缺陷修复：`repo-analysis → code-change → python-checks/项目检查`。
2. 文档维护：`repo-analysis → docs-change → docs-checks`。
3. 回归测试：`repo-analysis → regression-tests → mutation-review`。

以上箭头默认表示一个任务合同内的插件阶段，不是 07 的跨任务 DAG 边，也不要求每个箭头启动一次模型。
改动完成后由核心固定候选，检查阶段消费该尚未 PASS 的候选，再交主模型 verdict；不要求先验收改动才能开始检查。
阶段间沿用同一合同及其证据链，不创建多余 commit；确定性检查由固定 runner 完成。
若调查已由规划阶段完成且输入仍有效，可消费其固定产物，不为了凑节点重复调查。
只有拆成多个可独立验收合同的任务，才形成跨任务依赖；下游此时依照 07 等待上游接受及真实可用基线。
组合中的核心范围、授权、证据与验收门禁始终运行，工作流检查只能补充质量证据。
每类组合至少包含一个成功 fixture 和一个质量失败 fixture，不能只验证 happy path。

### 4.3 各类验收区别

缺陷修复应以具体触发条件说明修复前后行为；已有测试通过不能代替相关回归证明。
文档维护检查本地引用、代码示例与实际行为一致性；结构检查通过不能代替内容复审。
回归测试要能识别目标缺陷；反测按主模型审阅的方案选择旧实现或受控变异。
不要求所有文档任务做突变测试，也不为了统一格式给低风险改字新增无意义测试。
检查命令采用 05 的 argv 或明确平台实现，支持平台仅用 `linux/macos/windows`。
缺少目标平台检查时明确失败或声明不支持，不能静默跳过后宣称平台通过。
单纯生成 Markdown、补丁或 JSON 不等于完成任务；验收必须指向固定候选和检查来源。

### 4.4 资源和权限

模板、示例、schema 和检查定义都进入 06 的完整内容锁。
项目命令由项目配置和正式合同显式提供，插件不从 README 文本中抓取后直接执行。
草稿中的检查只做静态校验；未经审核不能以“插件预检”为名执行模型生成命令。
首批插件默认不请求联网、依赖安装、提交、推送或部署；确需操作时仍走已有授权交集。
普通执行器受保护路径不变，不能借 `docs-change` 修改 AGENTS.md 或管理目录。
插件开发本身属于工具链维护，不作为普通任务插件可自行实施的内容。

## 5. 预计文件范围

- 新增 `plugins/repo-analysis/`、`plugins/code-change/` 和 `plugins/python-checks/`。
- 新增 `plugins/docs-change/`、`plugins/docs-checks/`。
- 新增 `plugins/regression-tests/`、`plugins/mutation-review/`。
- 新增 `workflows/` 中三组声明和类型化输入输出样例。
- 新增小型 fixture 仓库/生成器及离线集成测试，不向实际项目注入故意缺陷。
- 如需提取技能资源，只改 `.agents/skills/` 源文件；本阶段通过已验证的平台入口运行 `sync-adapters` 同步副本，12 再整体核对。兼容命令是 `bash scripts/dispatch-pi.sh sync-adapters`，无 Bash 时用等价的 `python scripts/pi_dispatch.py sync-adapters`。

实际目录与资源命名在实施合同中固定；不为每个插件预先建立空代码模块。

## 6. 实施步骤

1. 先定义共享产物类型、事实来源和执行报告字段，核对 06/07 的类型校验。
2. 建立 `repo-analysis` 与代码修复组合，打通固定候选、检查和主模型验收记录。
3. 建立文档组合，以本地链接和内容错误展示独立质量要求。
4. 建立回归测试组合，把执行侧自检与验收侧反测分开，保存固定候选证据。
5. 增加三平台命令变体及缺平台的负向 fixture，验证插件没有偷带 Bash 依赖。
6. 将组合样例交给 09，证明规划器可以引用现成能力而非重复输出完整规则。

## 7. 验收标准

- **08-A01**：三种工作流通过 manifest、锁、任务 DAG 与阶段类型校验；检查无需候选先 PASS，不引入验收依赖循环。
- **08-A02**：缺陷修复 fixture 能发现原缺陷并在固定候选上通过相关检查，失败修复不获接受。
- **08-A03**：文档 fixture 能识别失效本地链接；内容仍错误时主模型可以拒绝，即使格式检查通过。
- **08-A04**：回归测试 fixture 在目标缺陷或受控变异下失败，在正确候选下通过；只镜像实现的空测试不作为完成证据。
- **08-A05**：三类工作流仍受范围、授权与核心门禁控制，插件输出 PASS 不能绕过验收。
- **08-A06**：未审草稿不执行 setup/check；插件不能借检查安装依赖或写管理目录。
- **08-A07**：插件不绑定 Pi/Step 等品牌，切换已支持 profile 无需修改插件定义。
- **08-A08**：各声明支持的平台有可运行检查；缺平台实现或 shell 时报告具体缺口。
- **08-A09**：离线测试不调用真实模型、不依赖外部站点、不改写已有 `.agent/runs/`。

## 8. 兼容与恢复

插件集合为 v2 的显式能力；旧合同不自动改写成工作流，也不自动启用新增插件。
模板或检查改动生成新锁并重新审核相关输入，活动 attempt 保留其原资源快照。
某组合失败时保留产物和检查证据，由主模型决定修复实现还是修订合同，不静默替换插件。
可停用新工作流并继续使用旧单任务入口；已产生的 v2 证据仍按其原协议读取。
首批示例不足以覆盖新任务类型时，应新增明确产物与验收适配，不能仅更换提示词声称兼容。

## 9. 后续合同拆分建议

以下是后续小工作包建议，正式派遣前需重新绑定基线、范围、profile、预算和授权。

1. 共享产物与代码修复组合：先验证核心契约和离线闭环。
2. 文档维护组合：交付本地链接检查和内容复审样例。
3. 回归测试组合：交付旧实现/变异对照及验收侧边界验证。
