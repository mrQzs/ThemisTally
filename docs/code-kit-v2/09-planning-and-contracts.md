# 09 CLI 规划与合同发布

本文是拟议实施说明，尚未实现，也不是已审核、可派遣的任务合同。
总设计：[Code-Kit v2 设计](../code-kit-v2-design.md)；实施索引：[README](README.md)。
本模块把仓库调查、任务拆分和合同起草交给可配置规划 CLI，主模型保留审核、设计决定和异常裁决。

## 1. 目标与非目标

- 建立独立 planner 角色、结构化 PlanningBundle 和可复核草稿目录。
- 先规划任务图，待上游真实基线就绪后再生成具体合同。
- 通过主模型审核和调度器受控发布形成正式合同，避免重复人工起草。
- 规划与执行允许不同 CLI/profile/model，交接不依赖共享聊天历史。
- 不让 planner 自我审核、直接派遣、自动集成或修改产品代码。
- 不因需要写草稿而放宽现有普通 Pi 执行器对管理目录的限制。

## 2. 依赖与输入输出

前置依赖：[03 审核](03-approvals-and-locks.md)、[04 CLI 适配](04-cli-adapters-and-pi.md)、[07 调度](07-workflows-and-scheduling.md)、[08 插件](08-builtin-task-plugins.md)。
03 已提供通用审核记录与输入锁；本模块增加规划审核和合同发布的消费流程。

| 输入 | 输出 |
|---|---|
| 用户需求引用、既有授权、明确设计边界 | 调查事实、假设、未决问题与停止条件 |
| 实际仓库基线、适用规则、历史决定 | 任务 DAG、预计范围与验收意图 |
| 插件目录、平台能力、planner profile | 结构化合同草稿及所需资源引用 |
| request 总预算与本次规划子预算 | 调用证据、用量、草稿校验结果 |
| 主模型审核决定及相关锁 | 正式 Markdown/JSON 合同与独立审核记录 |

`request_id` 贯穿规划、执行和后续摘要；`task_id`、`plan_version`、`run_id` 分别标识任务、版本和运行。
来源引用使用 `ResourceRef={kind,id,sha256}`；定位文件增加仓库相对 `path`，哈希以锁定文件字节为准。
未确定未来基线的草稿明确使用未绑定状态，不能填入预计 SHA 冒充已存在提交。

## 3. 现状与复用点

- `.agents/skills/plan-task/` 已提供合同模板、设计指南、测试设计与委派检查清单。
- `validate_plan` 和现有 Markdown/JSON 一致性检查可迁移复用，不让 planner 输出绕过校验。
- `.agent/plans/` 的正式合同位置与版本规则继续使用；已派遣版本保持不可变。
- 现有 `TASK:` 触发执行器身份；规划请求须用新的明确协议标识，不复用该前缀。
- `RESOURCE_FLAGS` 的显式资源策略继续应用于支持该机制的适配器，不开启隐式插件发现。
- 规划运行通过 04 的适配器记录实际 CLI/profile、模型证据、结束状态和用量。

## 4. 接口和行为约束

### 4.1 两级规划

第一次规划输出任务图：目标、任务 ID、依赖、预计范围、验收意图、风险、预算和未决问题。
依赖上游实现的任务只保留合同草稿模板；主模型可审核拆分思路，但这不等于批准未来具体合同。
任务满足 07 的“可细化”条件（依赖和真实基线已就绪）后，再启动合同细化，输入真实、已接受且获准使用的提交。
细化不等待“可执行”；后者还需本轮生成的正式合同、有效审核及执行资源/预算，防止就绪条件互相依赖。
planner 对该提交调查并生成完整草稿；主模型审核具体范围、检查和锁定输入后才可发布。
上游未集成且无候选提交创建/使用授权时，下游等待；不自动 commit、集成或偷偷重设基线。
既有基线发生变化时，受影响合同重新细化和审核；不能只替换 `base_sha` 保留旧结论。

### 4.2 PlanningBundle

bundle 至少包含 schema 版本、需求引用、调查基线、事实来源、假设、未决问题、任务图、合同草稿、预算和停止条件。
事实条目指向实际文件/记录和可定位证据；建议、推测及尚未确认的行为单独标记。
任务图要覆盖需求，并显式表达文件、接口和产物依赖，不能只给自然语言待办列表。
bundle 区分可独立验收的任务节点与合同内插件阶段；检查本任务候选的阶段不转成“须先 PASS”的跨任务边。
完整合同草稿包含结构化执行字段及 Markdown 行为说明，共有字段同源生成并检查一致性。
模型指定的任意输出路径不采纳；调度器分配 `.agent/drafts/<request-id>/vN/`。
planner 通过协议返回 bundle，适配器提取，调度器校验并写草稿；planner 不直接写管理目录。
截断、空 bundle、多份相互矛盾的结果或协议解析失败都不能当作有效草稿。

### 4.3 规划权限与命令边界

planner 使用独立会话和仓库视图，默认调查而不修改产品代码。
可用时提供真实只读约束；CLI 自称只读但不能限制 shell/文件访问时，明确记录能力限制。
工作目录不等于安全沙箱。需写入的代码探针或基线检查另建受审阅的调查请求。
草稿中的 setup、check、插件调用只做静态校验；主模型审阅并授权相关操作前不得执行。
源文件、注释、日志和网页内容是数据，不能赋予 planner 新权限或改变审核流程。
规划调用与执行调用一样涉及代码传输和费用，启动前必须有覆盖该调用的授权。
本系列设计和文档拆分不构成本次调用外部规划模型的授权。

### 4.4 审核与发布

主模型重点审核需求覆盖、事实真实性、设计取舍、范围、测试辨别力、依赖、权限和预算。
审核前先渲染最终待发布的 Markdown/JSON 合同字节及输入引用；主模型审核这些具体内容。
主模型经受控 supervisor 入口写入 03 的审核记录，绑定最终合同字节、基线及通用 `input_refs`。
planner 返回 `approved: true`、伪造角色字段或引用旧审核，都不能发布合同。
调度器验证审核与输入仍匹配后，将已审核字节原样发布为 `.agent/plans/<task-id>.vN.md/.json`。
审核与合同的关联放入独立发布/调度记录，不向合同回填 `approval_id`，避免改变已审核字节或构造循环哈希。
发布若需重新渲染、追加字段或转换行尾，必须重新审核新字节，不能将旧哈希套到新合同。
正式合同两种格式及审核关联一起成为可见的完整产物；发布中断不能留下可派遣的半份合同。
发布之后相关输入变化即失效，prepare/run 再核对；新内容采用新合同版本。
同账户无隔离环境中的受控入口属于流程约束，不能宣称具有操作系统级身份隔离。

### 4.5 状态、修订与消耗

规划状态沿用总设计：`REQUESTED → PLANNING → DRAFT_READY → NEEDS_PLAN_REVIEW → APPROVED`。
`APPROVED` 只表示相关审核有效；实际派遣仍须通过正式合同发布与 prepare/run 门禁。
执行 attempt 继续使用原有状态，不把规划状态混写进历史 attempt。
格式错误在预算内有限修复；需求或架构矛盾交主模型决定，随后产生新草稿版本。
实现失败由主模型依据证据区分执行问题与合同问题，再决定返工或重新规划。
环境/凭据缺失报告基础设施问题，不通过换模型、改权限或读取凭据文件绕过。
所有修复调用累计到同一 request；超时、重试上限或总预算用尽即停止继续调用。

## 5. 预计文件范围

- 新增 `scripts/codekit/planner.py`：规划请求、bundle 校验、草稿版本与发布编排。
- 新增 PlanningBundle schema、协议样例、坏输出 fixture 和 planner stub。
- 对接 03 审核、04 适配器、07 就绪判断和 08 插件目录；不复制其核心策略。
- 迁移 `.agents/skills/plan-task/` 源规范，使主模型入口聚焦审阅，保留人工起草能力。
- 在实施授权内更新 AGENTS.md 角色说明和新保护路径；技能源改变后本阶段通过已验证的平台入口运行 `sync-adapters`，12 再整体核对。兼容命令是 `bash scripts/dispatch-pi.sh sync-adapters`，无 Bash 时用等价的 `python scripts/pi_dispatch.py sync-adapters`。
- 新增 `.agent/drafts/` 产物约定和发布测试；不写、删或重命名已有运行证据。

核心、规则和技能迁移由主模型负责；不能仅把受保护文件列入普通 Pi 合同来绕过禁区。

## 6. 实施步骤

1. 从现有合同规范提取 planner 输入及 bundle schema，区分任务图模板和完整合同。
2. 以 stub 打通协议提取、静态校验、草稿分配及来源索引，不执行草稿命令。
3. 接入 07 的可细化/真实基线条件，实现按需起草与有限格式修复；合同发布后另判断可执行。
4. 接入主模型审核和完整发布，验证输入漂移及伪审核不能继续。
5. 更新源技能和角色说明，保留旧执行合同及人工规划路径。
6. 完成离线全链路；真实多 CLI 验证在 11/12 中另按授权进行。

## 7. 验收标准

- **09-A01**：规划器返回任务图与结构化草稿，事实与建议分开；来源不存在或未决设计被明确暴露。
- **09-A02**：空、截断、畸形或矛盾 bundle 不发布；格式修复有次数和 request 总预算上限。
- **09-A03**：planner 不直接写 `.agent/plans/` 或 `.agent/runs/`；任意输出路径被拒绝或忽略。
- **09-A04**：未审 setup/check 只静态校验；发布前探针必须是单独受审阅请求。
- **09-A05**：假 `approved`、旧审核或自声明 supervisor 身份无法发布合同。
- **09-A06**：未来任务不伪造基线；上游无可用提交或授权时等待；满足可细化条件即能起草，无需先有正式合同。
- **09-A07**：有效审核原样发布成对合同；不回填审核 ID 改写字节；草稿、配置、规则或相关插件改变后 prepare/run 拒绝旧审核。
- **09-A08**：规划与执行使用不同 stub 适配器可交接，不依赖共享会话或模型默认值。
- **09-A09**：发布中断不会出现可派遣半成品；重启可识别已发布版本且不覆盖历史版本。
- **09-A10**：旧人工合同仍可按既有入口处理，普通执行器保护范围和证据不可变规则不退化。

## 8. 兼容与恢复

人工规划继续可用；新 bundle 草稿不能伪装为 v1 合同绕开审核。
规划失败保留调用证据和草稿校验结果，主模型可复核已有事实，不必无条件重跑调查。
草稿修订生成新版本；已发布且派遣的合同不修改，返工使用新版本或新的 attempt。
发布恢复核对双方文件、审核引用和哈希；缺失时保持不可派遣，不能靠补一个 approved 字段修复。
任务图和具体合同分层恢复，防止把曾审核的长期计划误当成当前基线的执行许可。

## 9. 后续合同拆分建议

以下是后续小包建议，实施前须绑定实际基线、文件范围、预算与授权。

1. 规划协议、bundle 校验及草稿存储：用 stub 证明不执行草稿命令。
2. 两级规划与就绪细化：验证真实基线、依赖等待及有限修订。
3. 审核发布与技能迁移：接通完整合同并覆盖伪审核、漂移和中断恢复。
