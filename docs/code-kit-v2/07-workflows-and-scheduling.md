# 07 工作流与任务调度

本文是拟议实施说明，尚未实现，也不是已审核、可派遣的任务合同。
总设计：[Code-Kit v2 设计](../code-kit-v2-design.md)；实施索引：[README](README.md)。
本模块将明确的任务及插件组合为可检查的依赖图，管理就绪、并行、预算和停止条件。

## 1. 目标与非目标

- 表达任务顺序、类型化产物映射、写入范围和互斥约束。
- 在满足审核、真实基线和依赖条件后才允许任务派遣。
- 将规划、执行及其他角色的消耗归集到同一需求，限制自动重试和返工。
- 独立验证调度器，不要求 09 的规划 CLI 已完成。
- 不让 DAG 自动决定架构、修改合同、接受失败结果或批准集成。
- 首期不支持非 Git 产物存储、不承诺分布式集群调度。

## 2. 依赖与输入输出

前置依赖：[03 审核与锁定](03-approvals-and-locks.md)、[06 插件](06-plugin-manifests-and-locks.md)。
插件层已经承接配置和平台能力；本模块消费解析后的结果，避免复制其规则。
首次验证使用人工创建并通过审核的正式合同或离线 fixture；09 是后续生产者，不是本模块前置依赖。

| 输入 | 输出 |
|---|---|
| 工作流节点、插件精确版本、依赖和输入映射 | 经校验的 DAG 及节点错误 |
| 正式合同、相关审核与输入锁 | 可派遣节点集合及等待理由 |
| 已接受结果、授权的基线提交和固定产物引用 | 下游输入绑定及基线确认 |
| request 总预算、任务子预算和并发上限 | 调度决定、用量累计和停止原因 |
| attempt 状态和主模型裁决 | 任务级状态变化与可供 10 索引的事件 |

`request_id` 是全局预算根；`task_id` 标识任务，`plan_version` 标识合同版本，`run_id` 标识一次运行。
产物与审核输入采用 `ResourceRef={kind,id,sha256}`；文件定位另加仓库相对 `path`。
工作流锁和产物引用哈希取实际锁定文件字节；引用不能仅靠“最新结果”或可变文件名。

## 3. 现状与复用点

- `cmd_prepare`、`cmd_wait`、`cmd_status` 已管理单次 attempt，继续作为底层能力。
- `record_candidate` 提供固定候选，`evaluate_gates` 和 `cmd_verdict` 提供验收边界。
- `cmd_metrics` 的 attempt 用量可作为预算事实来源之一，不能把缺失费用视为零。
- 现有状态名继续保留；新任务图状态是其上层投影，不改写历史状态语义。
- 现有进程监督仍由 05 负责，DAG 调度不另起一套超时和进程树逻辑。
- 当前缺少项目级 DAG、任务输入映射和 request 累计预算，需要新增。

## 4. 接口和行为约束

### 4.1 任务图、任务内阶段与类型约束

任务 DAG 的节点对应可独立验收的任务合同；节点至少声明 ID、阶段组合、输入输出、任务依赖、预计写范围和子预算。
任务内阶段声明所用插件版本、角色、输入映射与检查。任务 DAG 边和阶段顺序分别建模，不混用节点 ID。
同一任务图中节点 ID 唯一；跨任务边必须指向存在的任务，图必须无环。
上游输出的 schema 必须满足下游输入，不能在执行中靠自然语言猜测字段。
缺少必需输入、平台检查实现或运行能力时，预检失败而非调度后跳过。
列表书写顺序不决定业务顺序；只有依赖、锁和调度策略决定节点先后。
工作流定义也作为审核输入锁定；改边、改输入映射或改预算均按相关变化重新审核。
单个合同内的“改动 → 固定候选 → 检查 → verdict”是阶段顺序：检查可以消费尚未 PASS 的固定候选。
这些阶段共用合同及其证据链，不因每个箭头创建新任务、要求新 commit，或等待本任务先通过验收。

### 4.2 就绪与真实基线

区分“可细化”和“可执行”：前者允许 09 根据真实输入起草具体合同，后者才允许 prepare/run。
任务满足以下前两项即可进入合同细化；规划调用自身另核对规划授权、profile 和预算，不要求尚未生成的正式合同。
任务仅在以下条件全部成立时成为可执行、可派遣项：

1. 必要上游任务已获接受，并有可核对的固定产物和验收记录；无前置任务时使用已确认的当前输入。
2. 所需代码已存在于真实且获准使用的基线提交，提交在当前仓库可解析。
3. 本节点有针对该基线生成的具体正式合同、有效审核和一致输入锁。
4. 平台、profile、插件能力、有效权限及预算仍满足要求。
5. 与正在运行任务之间没有未处理的文件、接口、产物或互斥冲突。

上游通过检查不自动等于获准作为下游基线；接受和集成/使用授权分别核对。
上游只有未提交补丁且没有创建或使用候选提交的授权时，下游保持等待。
调度器不自动 commit、集成或替换 `base_sha`；由主模型按既有授权解决基线来源。
未来任务可有草稿模板，但该模板不构成可派遣合同。09 在“可细化”时生成具体草稿，不等待“可执行”而形成循环。
上述上游接受要求只约束跨任务依赖，不阻止同一合同的检查阶段读取本任务尚待验收的固定候选。

### 4.3 并发、重试与结果接受

同文件、同模块或显式互斥资源的写任务默认串行；不同文件也检查接口及产物依赖。
并行需要已记录的独立性判断和独立 worktree，不能只按文件名无交集推定安全。
调度时原子领取节点；同一合同不得因两次轮询创建重复活动 attempt。
attempt 结束后先进入复审流程，不能把退出码 0 当作节点接受事件。
失败归因由主模型负责；执行问题可按裁决返工，合同问题必须生成新版本。
重放、合并或重基准产生新候选时重跑有关检查，不继承旧候选的 PASS。
已运行的 attempt 和审核记录保留；重试只添加运行，不覆盖旧证据。

### 4.4 预算与停止

预算包含调用次数、时限、并发数，以及能够观测到的 token/费用。
以 `request_id` 累计 planner、executor、独立复审工具及可选 observer 消耗。
更换 CLI、角色、任务名、合同版本或 attempt 都不能重置 request 总额。
子预算用于局部限额，不能超出全局余量；并行启动前预留可用额度，结束后对账。
实际用量缺失标记 `unknown`，保留调用次数和时限，不能把 unknown 当免费继续无限调用。
账目以原始调用/提供商计费记录的稳定 ID 去重；摘要和状态投影不得再记一笔费用。
不同币种分别累计，除非有明确且可追溯的换算策略；当前主会话不可观测用量不伪造为零。
提供商无法硬限制金额时，如实标注为观测预算；用次数和时限提供可机械执行的停止边界。
达到停止条件后不再启动新节点；正在运行任务按预先确定的取消/收尾策略处理并保存证据。
剩余任务、已经花费的额度和所需主模型决定要能从状态中读出。

## 5. 预计文件范围

- 新增 `scripts/codekit/workflow.py`：DAG、输入映射、就绪判断和冲突检测。
- 新增工作流 schema、`workflows/` 样例及离线 fixture。
- 增加 request 预算账本与调度领取记录，具体事件格式复用 01 的协议。
- 对接既有 prepare/run/status/metrics/verdict，不改写历史 attempt。
- 新增调度与预算测试；10 再提供项目状态投影和恢复简报。
- 核心文件和相关策略纳入保护范围；普通 Pi 执行器限制不变。

## 6. 实施步骤

1. 实现纯 DAG 与类型映射校验，覆盖无环、缺依赖、错误输出和平台缺口。
2. 以人工正式合同 fixture 接入就绪判断，验证实际提交、审核和输入锁。
3. 实现原子领取及冲突规则，先提供顺序调度，再放开已证明独立的并行。
4. 接入 attempt 与主模型结论；把“执行结束”和“任务接受”分成不同事实。
5. 实现 request 预算累计、并行预留和有限重试，明确 unknown 的停止策略。
6. 暴露稳定事件与只读状态接口，供 09 生产任务、10 投影状态。

## 7. 验收标准

- **07-A01**：循环、悬空边、重复节点、错误输入类型和缺字段均在派遣前被拒绝。
- **07-A02**：人工合同构成的离线工作流可完成顺序调度；任务内检查可读取尚未 PASS 的固定候选，无需启动规划 CLI。
- **07-A03**：上游未接受、缺真实提交、缺基线使用授权或审核过期时，下游保持等待并给出理由。
- **07-A04**：重叠写范围默认串行；有接口依赖的不同文件任务也不能错误并行。
- **07-A05**：重复调度请求只领取一次；重启后不能因丢失内存状态重复启动活动节点。
- **07-A06**：attempt 退出 0 但未获验收时，下游不启动；拒绝验收的结果不被消费。
- **07-A07**：跨角色、CLI、版本和重试的消耗累计到同一 request，子预算不能绕过总限额。
- **07-A08**：并行请求不会各自花掉全部剩余额度；unknown 用量不按零处理，重试有机械上限。
- **07-A09**：重基准或合并后候选重新检查；旧 PASS 不能批准新候选。
- **07-A10**：停止或恢复保留全部 attempt；无正式合同但依赖/基线已就绪的任务可细化而不可执行；不自动提交或改写基线。

## 8. 兼容与恢复

单任务旧入口继续使用既有流程；新工作流可把一个正式任务视为单节点图，但不伪造 v2 审核。
领取记录与 attempt 的实际落盘状态需对账；出现“已领取未启动”或“已启动未记账”时先恢复事实。
不能仅凭内存锁或工作流终态推定外部进程已经结束；恢复时调用底层运行状态与证据接口。
图或预算状态损坏时停止新派遣，并从不可变运行/审核证据及预算记录恢复，不修改原始证据。
工作流定义变化使用新版本；活动节点继续引用启动时输入，受影响的待运行节点重新审核。

## 9. 后续合同拆分建议

以下小包需要在实施时另写正式合同并绑定实际基线、范围、预算和授权。

1. 工作流 schema、DAG 与类型校验：先交付无进程调用的静态能力。
2. 就绪、基线与并发领取：使用人工合同和 stub 证明调度正确性。
3. request 预算、重试与恢复：覆盖跨角色累计及崩溃窗口。
