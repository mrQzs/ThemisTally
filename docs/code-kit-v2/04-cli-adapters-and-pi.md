# 04 CLI 适配器与 Pi 迁移

状态：拟议实施说明，尚未实现；不是已审核合同，不授权真实模型调用或 CLI 安装。
总纲：[完整设计](../code-kit-v2-design.md)；导航：[实施索引](README.md)。
对应总设计：第 4.3、9 节及 P1，向 11 的第二 CLI 接入提供接口。

## 1. 目标与非目标

把 Pi 专有参数、能力探测和事件解释从调度核心移入 adapter，Pi 成为首个内置实现。
不同角色可选择不同已支持 CLI，核心只处理统一请求、能力和证据。
保持现有模型核对、工具审计、终止判定和候选门禁；不能以兼容新 CLI 为由减弱它们。
不把替换 argv 第一个元素视为接入新 CLI，也不以 stub 测试冒充真实协议支持。
adapter 构建调用并解释协议；进程启动、超时、取消、进程树和 shell 执行由 05 负责。
不在本模块选择第二 CLI 或预设其命令参数，具体选择与证据验收交给 11。

## 2. 依赖与输入输出

依赖：[01 基准与公共协议](01-baseline-and-protocols-审阅增强版.md)、[02 配置与角色绑定](02-config-and-profiles-审阅增强版.md)。
输入：锁定的角色请求、有效 profile、平台和工作目录、允许工具、协议能力要求。
输出：Invocation、能力/版本探测记录、标准化事件、结果报告与用量/身份的证据等级。
使用 01 的事件、资源引用和 `request_id`/`run_id`，不能按 vendor 会话 ID 替代本地运行 ID。
调用描述交给 [05 跨平台执行](05-cross-platform-runtime.md)，原始证据引用交回核心归档。
03 的审核锁定发生在调度层，adapter 不拥有批准或发布合同权限。

## 3. 现状与复用点

`resolve_pi_command` 已处理可执行入口、覆盖变量和 Windows npm shim。
`pi_preflight` 已核验 Pi 参数、模型列表和认证就绪，应拆为 Pi 专有探测逻辑。
`summarize_events` 已解释 Pi JSON 流、模型、工具和最终报告，是迁移的行为基准。
`cmd_run` 负责总调度，应逐步替换专有调用，保留证据目录和候选流程。
`RESOURCE_FLAGS` 关闭 Pi 扩展、技能和提示模板自动发现；首期继续保留这一受控加载行为。
`tests/stub_pi.py`、`tests/stub_pi_help.txt` 和现有回归提供离线协议样本。
迁移先保持输出事实与失败判定一致，不同时重写所有事件格式或报告逻辑。

## 4. 接口和行为约束

### 4.1 最小适配器协议

| 接口 | 输入与输出 | 禁止行为 |
|---|---|---|
| `probe(runtime)` | 命令/平台 → 版本、入口、协议与能力记录 | 不调用付费模型，不打印凭据 |
| `validate_profile(profile)` | 模型与选项 → 合法值、角色能力诊断 | 不静默改模型或思考级别 |
| `build_invocation(request)` | 锁定请求 → argv、stdin/请求文件描述、cwd、环境变量名 | 不运行进程，不拼通用 shell 模板 |
| `normalize_event(raw)` | 单条原始记录 → 标准事件及原始引用 | 不丢弃未知记录来伪装完整 |
| `collect_result(events)` | 完整/不完整流 → 状态、报告、身份、工具和用量 | 不因退出码为 0 直接宣告成功 |

Invocation 只描述已核验的调用；实际进程环境由核心过滤后交给 05。
请求文件由调度器分配与写入，adapter 不接受模型指定的任意输出路径。
schema 和能力 API 需要版本号，不认识的协议版本在启动前阻塞。
probe 只使用无模型调用的本机帮助/版本/能力入口；无法无费用核验的项目标明待授权验证。

### 4.2 能力与角色要求

能力分别声明 `streaming_events`、`terminal_event`、`model_identity`、`tool_events`、`usage`、`read_only_mode`。
同时声明支持平台、可用工具、输入协议和资源加载方式，不能用一个 `supported=true` 概括。
声明须关联版本与探测/样本来源，只有宣传材料或配置值时不能当作已验证事实。
角色/工作流先给出必要能力集合，再与 adapter 能力求匹配；缺少必要能力就阻塞该角色。
planner 的只读请求与真实环境约束分别报告，工作目录限制不等于文件系统沙箱。
调查角色可以使用不同证据要求，但不能因此直接满足代码执行验收。
shell 名称配置与 CLI 内部工具能力分离；Pi 的 bash 工具不会因 Windows 配置自动变成 PowerShell。

### 4.3 原始流与统一证据

保留经过既有脱敏流程处理的原始流，以及标准化事件流，二者建立可回查引用。
事件遵循 01 的 schema，至少包含 run、序号、时间、角色、类型、payload 和原始记录引用。
未知事件保留并标记；影响必要审计完整性时结果为不完整，不能跳过后继续 PASS。
截断 JSON、无终止事件、乱序/重复记录、解析器异常和 CLI 非零退出要分别留证。
报告文本不能替代工具事件，模型所说“测试通过”不能替代独立检查证据。
请求模型、CLI 回报模型、提供商回报模型分别存储，缺项使用 `unknown`。
实际模型缺失或与锁定值不符不能按正常执行通过；保留 G1 的现行关键语义。
思考级别只回报请求值时标明证据等级，不虚构提供商已确认该级别。
用量拆分输入/输出 token、货币金额和来源；未回报费用为 `unknown`，不能归零。
累计预算仍以 `request_id` 汇总，换 CLI 或 vendor 会话 ID 不重置累计值。

### 4.4 Pi 迁移边界

先用同一批 Pi fixture 对迁移前后做行为对照，保留错误类别与必要原始字段。
v1 合同路由 Pi adapter，v2 通过 profile 选择 adapter，核心不再访问 Pi 参数常量。
Pi 兼容环境变量仅在 v1 路径解释，v2 使用 02 的锁定 profile。
默认禁止未声明的 Pi 原生资源发现；06 的任务插件由核心显式编译，不等于 Pi 原生扩展。
需要真实 Pi 试跑时单独核对现有调用授权、所选 profile、预算及模型/环境精确 ID。

## 5. 预计文件范围

- 新增 `scripts/codekit/adapters/` 的协议、注册表及 Pi 实现，按职责提取实质代码。
- 从 `scripts/pi_dispatch.py` 迁移 Pi 解析和预检，保持 v1 调用与历史读取兼容。
- 在 `tests/` 补充通用 adapter fixture、Pi 对照和异常流测试。
- 按需更新环境核验文档及源技能，明确 Pi 专有能力与核心能力边界。

受保护调度核心及源技能由主模型在后续实施授权下直接修改、复核；普通合同不能越权。

## 6. 实施步骤

1. 从现有 Pi 测试固定必要事件、模型核对、报告和失败类别基准。
2. 建立通用协议与注册表，以只输出固定数据的离线 adapter 验证核心边界。
3. 将 Pi 的命令解析、profile 校验和事件规范化迁入内置实现。
4. 把 `cmd_run` 接到 Invocation 和结果接口，进程监督调用仍由共享 runner 执行。
5. 对比原流程，补齐异常流，再向 11 提供第二真实 CLI 的协议接入清单。

## 7. 验收标准

- **04-A01**：Pi 原流程的必要证据、模型核对与门禁回归保持一致。
- **04-A02**：核心用 adapter 注册表选择实现，未知 adapter 明确阻塞且无模型进程启动。
- **04-A03**：stub 可验证通用接口，但能力报告明确标为离线模拟而非真实 CLI 支持。
- **04-A04**：缺结束事件、实际模型缺失/不符、工具事件缺口均不能得到正常执行通过。
- **04-A05**：畸形、截断和未知事件保留来源；标准化流不能掩盖原始流异常。
- **04-A06**：用量缺失记 `unknown`，请求、CLI 和提供商模型字段不互相填补。
- **04-A07**：probe 不调用模型；缺角色所需能力时报告缺口，不通过换模型自动绕过。
- **04-A08**：adapter 不自行启动/终止进程；平台 runner 接收可复现 Invocation。
- **04-A09**：v2 不受 Pi 兼容覆盖变量改写，Pi 资源发现仍按明确策略受控。

## 8. 兼容与恢复

按旧 schema 读取 v1 attempt，不要求历史事件具有新增标准化字段。
新解析器失败时保留原始流、stderr、调用快照与未完成状态，不丢弃已有证据重跑覆盖。
中断后恢复优先依据原始记录和版本化 parser；不把新规则套用为“修正旧历史”。
需换 adapter/profile 的重试形成新运行并重新预检，保持同一 request 的预算归属。
回退旧入口仍遵守旧门禁；不能靠回退跳过 v2 审核或处理新版草稿。
