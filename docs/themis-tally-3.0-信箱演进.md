## 1. 结论

- **取代的是信箱的传输与协调做法**：模型手写的信件文件、目录锁、轮询。
- **保留的是两样**：岗位之间发有类型的消息并全程留痕；落盘的只追加账本，内核是唯一的状态写入者。2026-11-12 一晚没有丢过信，内核中途换代任务照常接着跑，所有事情都能从账本还原，靠的就是这两样。
- **分工**：Quizs 实现工人这一半（领启动清单、发事件、心跳、用 `mail_send` 交割），内核实现中枢这一半（账本、排队与租约、裁决）。
- **不一次推倒**：信箱在内核正中间，两套实现加四百多条三边对照的契约。分四步，每一步都能单独验收、单独回退。

依据是用户自己的两份材料，讲的是同一套东西：

- `docs/13-multi-session-communication.md`：Claude Code 的多个会话之间不直连，都注册到一个中枢；每个会话一条带序号的事件流，断线按序号续传，重复帧检测；跨端交互是带请求号的请求与应答，可取消；工人有代数，旧工人的应答被丢弃；干活靠领取、确认、心跳；有容量与调速。
- 上位规范 `设计文档_修订完整版.md` 第 8–10 章：内核与工人走私有管道上的 JSON-RPC；每个请求带 `attempt_id`、`kernel_epoch`、`fence`；lease 30 秒、心跳 5 秒；取消是有审计的状态转换；`mail_send` 是字段严格的工具；锁目录由数据库的唯一占用索引与 lease 取代。

**不照搬的**：Claude Code 的中枢在云端，还有设备信任与多端挂载。TT 是本机的，中枢就是内核；界面只有桌面端一个，经本机服务访问内核（桌面端设计 D2、D4）。

## 3. 目标形态

照上位规范第 8–10 章，不另起一套；从 `docs/13` 借的只有协议层的做法。

| 方面 | 现在 | 目标 |
|---|---|---|
| 工人怎么交差 | 最后一条消息末尾的 JSON 块，内核解析成信；协调人直接写信的字段 | `mail_send` 工具，字段严格，发信人、任务、围栏号由内核补入（上位规范 10.9） |
| 工人拿权限 | 内核按名册给工具白名单，事后审计事件流 | 启动清单加内核 broker 逐次裁决（上位规范 8.2、第 10 章） |
| 干活的登记 | 目录锁加执行标记；空闲 60 秒退出的 runner 进程 | lease 加心跳，过期先撤权再停进程；内核重启换代数，旧通道全部失效（上位规范 8.5） |
| 重活的并发 | 后台回归之间排队，其余各跑各的 | 车道：模型回合并行，机器上的重检查排队（借 `docs/13` 的容量与调速） |
| 观察者（界面、站主工具） | 轮询 `status`、读账本文件 | 账本事件带单调序号，按游标重放的事件流，经本机服务的 SSE 给界面（借 `docs/13` 的序号重放；桌面端 D7 本来就要） |
| 站主的操作 | 命令行加回信 | 带请求号、可查询幂等结果的调用（预览、确认号的做法已经是这个形状） |
| 取消 | 只有“停止”主任务 | 有审计的状态转换：先写撤权事件，后停进程 |
| 状态的落盘 | `state.json` 整份原子替换加 `events.jsonl` 只追加 | 不变的是“只追加、内核唯一写入”；存储换成 SQLite 是上位规范第 7 章的事，不在本文的四步里 |

## 5. 第 1 步的设计（r3 第 155 轮）

### 5.1 重活车道

- **进车道的**：内核自己起的、会把全部旧门禁跑一遍的活。
  - 战前门禁之后的基线检查（调度器的 `baseline`）；
  - 执行端交付之后的检查（`check --fresh`），含站主的 `exec-recheck`；
  - 落地时 `integrate` 在末端上的检查；
  - 战后门禁的变异检查（`mutate`）；
  - 后台回归与落地预演（现在各自经 `sweep_window` 排队，改成进同一条车道）。
- **不进车道的**：模型回合。工人在自己的回合里跑的命令（门禁端试跑自己的基准、执行端的自检）也不进，它们由回合的时限管。
- **做法**：信箱目录下一把目录锁 `.heavy`，沿用 `DirLock`（持有者进程不在了才接管）。在起子进程之前拿锁，所以各条检查自己的时限不把排队的时间算进去。等待有上限，超了照“没跑成”处理并写明是在排队。
- **拿锁的次序**固定为 `.sweep` → `.heavy` → `.land`，任何路径都不反着拿：落地要先排到车道、再拿落地锁，免得拿着落地锁排队、把新的执行端挡在外面。
- **看得见**：`status` 的“并行”一行写出车道里是谁、谁在等；账本记 `heavy.waited`（等了多久）与 `heavy.ran`。
- **并行名额**：有了车道，等车道的主任务会占着自己的 runner。信箱的 `runner.json` 里并行数相应调大，让每个在办的主任务都有 runner，模型回合照旧并行。这是运行参数，不是内核改动。

### 5.2 偶发红自动重跑一次

- 基线检查或执行检查的结果里，**只有全量回归（R01）一项与预期不符**时，内核原样重跑一次这次检查（仍在车道里）。第二次相符：照通过处理，账本记 `regression.flaky`，带第一次红的用例名；给协调人的摘要里写明“第一次红了哪几条、重跑通过”。第二次仍不符：照现在的做法判失败。
- 本片自己的检查（V、G）不符不重跑。
- 协调人的提示加一句：红的用例所在的路径不在候选改动的包里时，先写“提问”给站主，不直接返工执行端。

### 5.3 这一步不做

- 在途检查的取消：要先能登记、能安全地停整棵进程树并回滚状态，放到第 4 步。这一步只做“注定作废的不启动”：站主已要求更早的阶段返工时，内核不再为当前阶段起基线检查。
- 换存储、换 IPC、动工人的交付方式。
