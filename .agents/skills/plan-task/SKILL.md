# 规划任务合同

用户目标：$ARGUMENTS

（上一行在 Claude Code 中会替换为调用参数；在 Codex 中保持原样，此时参数就是用户调用本技能时附带的文字。）

你是规划器：负责调查、设计决定、拆分与验收设计，不修改产品代码。合同要让 Pi 执行器**不需要再做设计决定**就能完成，并让验收端能逐项核对。

## 09 planner 交接（离线能力）

仓库的 09 planner 只产生受校验的 PlanningRequest/PlanningBundle、任务图和候选合同建议。
它不授予批准、执行、发布或额外预算，不直接写 .agent/plans/、.agent/runs/，也不执行草稿
中的 setup/check。主模型必须审核固定的 Markdown/JSON 字节、输入闭包和来源后，才能通过核心发布
入口登记正式合同；人工按本文件直接起草的 v1 合同继续有效。没有真实 provider、CLI、原生进程
或外部连接器证据时，保持 NOT_RUN/BLOCKED，不能把离线 stub 的通过结果写成生产接线。

命令统一写作 `bash scripts/dispatch-pi.sh <子命令>`（它会找到可用的 Python 3.8+；也可直接用 `python scripts/pi_dispatch.py`）。

## 0. 先判断是否值得委派

按 [delegation-checklist.md](delegation-checklist.md) 判断。任务很小、根因未明、需要架构取舍或高风险语义未定时，说明理由，改为直接完成或先调查，不要硬写合同。

## 1. 调查仓库（只读）

- 读 AGENTS.md（仓库另有 CLAUDE.md 时一并读）、相关源码、测试、工具链与锁文件。
- 记录基线：`git rev-parse HEAD`、`git status --short`。基线必须是完整提交 ID。
- 任务依赖主工作区未提交的改动时，请用户决定提交还是排除；不要 stash、reset 或 clean。
- worktree 从基线提交创建：AGENTS.md、被测代码和测试辅助文件必须已在基线里。AGENTS.md 未提交时提醒用户。
- 中高风险任务：在当前工作区运行相关的现有检查，记录基线结果；已知失败写明用例与错误指纹。

## 2. 分清事实、假设与未决问题

- 事实写进 Repository facts；实现细节中的合理假设由你决定并写明。
- 只有会改变产品行为或授权范围的问题才问用户：一次问完，给出推荐选项。

## 3. 决定设计并拆分

- 接口、错误语义、并发与取消、兼容性都由你决定，不留给执行器。
- 每个子任务一个主要结果、可独立验证；有依赖的任务串行，后一个从前一个已接受的提交开始。
- 需要用户拍板的设计（新能力、存储格式、对外行为的变化），写成设计说明放在 `.agent/design/<主题>.md`。
  - 逐条列出需要用户决定的问题，附上你的建议；用户确认后再拆分。
  - 这个目录属于规划路径，运行期间编辑只记为备注。
- **改写算法、又要求结果不变时**，先在副本上完成新算法，再写合同：
  - 在测试里保留原实现的逐字副本作为标准答案；
  - 用大量带平局的随机小用例、再加接近真实形态的数据，与标准答案逐项比对；
  - 性能问题先分阶段计时再下结论。Windows 上 cProfile 每次函数调用都有明显的额外开销，调用多的函数会被严重放大。
  - 实机例子：对齐 DP 的主要瓶颈不是网格大小，而是精确分数沿路径累加后分母变成上千位的大整数。
  - 合同要写明“等价性已经用标准答案验证过，不需要重新证明；按规则实现，以比对测试为准，测试不通过时报告最小用例”。必要时直接把已验证的实现写进合同。
    - 实机例子：稀疏 DP 的合同给出了完整算法与取舍规则，执行器仍用约 950 秒、十几万字符从头推导等价性，中途几次推翻合同里正确的规则，最后写完代码、来不及写报告就超时了。
  - 这类任务的时限按“实现 + 测试 + 运行”估算，并留出余量。
- **要求与现有实现逐项一致时**（移植、兼容层），把参考实现放进基线并做成验收标准，不要在合同里意译接口：
  - 参考源码与参考测试放进基线，例如 `.agent/design/<主题>/`，记下来源修订与摘要，合同点名它是唯一规格；
  - 规划端在基线上提交 oracle 测试，并列入 forbidden_paths：
    - 参考测试的逐字移植；
    - 参考测试没覆盖的失败关闭用例；
    - 在固定输入网格上与参考逐项比较返回值与错误码的差分测试。

    派遣前确认 oracle 在参考实现上全部通过、在基线上失败；
  - 实机例子：KitExperiment 的 runtime 移植，前四份合同只给了意译的接口。
    - 合同里没有错误码、摘要编码、整数上界，也没有写被拒绝的 handoff 怎么处理；执行器又读不到参考，四个候选都与参考不同。
    - 其中一个还在“合同没写”的地方选了宽松做法，空观察也放行重放。
    - 改为“参考 + 三个 oracle”的 v2 一次完成：canonical 层与参考逐个定义的 AST 相同，26 个变异全部被抓住。
- **草稿验证统计失败用例时，把子测试算进去**：pytest 子测试失败显示为 `SUBFAILED`，只 grep `FAILED` 会漏掉只在子测试里失败的用例。实机上合同写“20 个测试函数失败”，执行器实测是 34 个。用 `-rA` 的汇总或 `--junitxml` 统计。
- **列出要改掉的旧断言时，写成“下列旧断言是错的，改为对同一输入断言参考的结果”**，不要只写“至少包括：- X”的列表。实机上执行器把这种列表读成了要断言的目标语义，报告了 4 处合同矛盾，并把 DoD 标成 blocked（它按参考做对了）。
- **进程与信号类合同要写明平台语义与中断语义**，并先在目标平台上实测。KitExperiment 的监督器 v1 合同漏了两处，都在复审时才发现：
  - 漏了 macOS 的平台语义：进程组只剩未回收的僵尸进程时，`killpg` 返回 EPERM，不是 ESRCH。候选在发 SIGKILL 时抛出 PermissionError。
  - 没有定义清理阶段收到第二次中断怎么办。
  - 纯 Python 吸收中断总有几个字节码的残留窗口，要写进 Non-goals，不要让执行器去追求做不到的“完全吸收”。
  - 往一段“出错必须落定”的序列里新增步骤时（例如 `mark_running` 之后、`finish` 之前），合同要写明这一步的异常（含中断）同样受保护。KitExperiment verified-review 的合同只列了钩子、`candidate_hash` 与 `finish` 抛出时怎么办；新增的流核对要把两个流各重读一遍，于是成了一段约一秒、不受保护的窗口，一次 Ctrl-C 就让操作停在 RUNNING。执行器照合同字面实现，是独立复审发现的。
- **截止时间、间隔这类数值规则要两侧把守，并与合同的字面值比较**：
  - 截止时间：探针只断言“没有提前结束”时，“每次中断都重置截止时间”的变异会存活。还要断言“没有延后”。
  - 上界：测试拿实测值与被测模块的常量比较，常量改大时界限随之变大。实机上轮询间隔用例与 `_REAP_POLL_SECONDS` 比较，“间隔改为 0.5 秒”的变异存活。合同写明“与合同中的数值比较，不与被测模块的常量比较”。
- **落盘记录与重放判定类合同，要对照判定规则逐条核对每一句“失败时判为 X”，并写明预先存在的文件怎么处理**。KitExperiment 的 posix-reconcile-integration 合同就漏了这一点：
  - 第 3 条说“观察记录写入失败时判为 START_UNKNOWN”；
  - 但证据目录里若预先有一份旧观察记录，按第 4 条的判定规则会读到旧记录，结果放行了一次确实启动过的运行（失败开放）。

  独立复审发现后由规划端补上：启动前确认两份记录都不存在。读证据文件还要考虑 FIFO（用 `O_NONBLOCK` 打开，否则会一直阻塞）、读取上限（fstat 之后文件仍可能增长），以及写入端的同一上限。
- **被监督或不受信的进程能写的文件，不能单独决定放行**。KitExperiment 的 supervised-operation-bridge 合同让“落盘记录决定状态”，子进程就伪造了“未启动”的观察记录，让一次确实运行过的进程被释放。
  - 实时路径要以本进程拿到的事实（监督器返回的运行对象）为准，并要求落盘记录与之一致；不一致一律判为未知。
  - 只能看记录的恢复路径，要在合同里写明同账户环境下“记录只是关联证据，不是认证”。
  - 恢复路径只处理旧控制器没来得及判定的操作。已判为 `START_UNKNOWN` 之类的操作不要按记录重判：那个判断用到了只在内存里的观察，记录却是子进程也能写的。KitExperiment restart-recovery 的规划端决定 L12。
- **两份状态先后更新时（先内存、后日志），第一步的非业务异常同样要让实例失效**。KitExperiment 的持久账本 v1 只让追加日志失败使实例失效，内存调用期间的一次中断却让实例继续可用：内存里有、日志里没有，之后追加的命令在重放时找不到前提，账本从此打不开。合同要写明：被调方自己的拒绝（例如 `ContractError`）之外，任何异常都让实例失效。
- **设计说明与合同在同一个提交里改**。durable-ledger 的设计说明写着“排序键”“幂等重放的 claim 不记”，合同写的正相反；执行器按合同实现并指出了矛盾。写合同时改了设计，就同步改设计说明。
- **合同要求转换路径时，写明不按字面规范化**：`os.path.abspath`、`normpath` 直接消去 `..`，内核却先跟随符号链接。durable-ledger v2 只写了“先转成绝对路径”，执行器与规划端草稿都用了 `abspath`，结果 `a/link/../ledger.db` 让创建把账本表写进了别的程序的库。写明用 `Path.absolute()`，或者让每一步都把同一个字符串原样交给内核；见 test-design.md 的路径矩阵。
- **比对式的守卫要比对完整的状态**：KitExperiment request-resume 的恢复只比对 `stopped` 记的第一个停止原因；请求已经停止之后再加的显式暂停（例如安全暂停）看不见，被一次恢复一并清掉。合同里写“比对 X”时，先确认 X 能表示所有叠加上来的变化（全部停止原因、序号或版本），否则就是只实现了一半的 CAS。
- **把用户决定写成合同前，先查清决定里每个条件在代码里何时成立**：KitExperiment resume-holds 的决定是“账本见过运行的操作不能判为未启动”，可是桥接要等运行结束才补登记开始，最常见的崩溃（运行中途）账本根本没见过。按文字实现完全合规，决定的本意却只覆盖了一半。同理，以原因文字去重时，两次同文字的暂停会合并成一项。
- **写“X 不改”之前，列出所有能产生同一结果的入口**：KitExperiment explicit-holds 的规划端决定为保住重启恢复按记录判未启动的路径，写了“`recover` 不改”。结果换一代之后，`recover(NOT_STARTED)` 成了运维把已判定的受监督运行判为未启动的第二条路，绕过了刚加上的规则。补一条“不许做某事”的规则时，把能做到这件事的每个方法都列出来，逐个决定拦还是不拦，并在合同里写明理由。
- **“是 str / dict / int”一律写成精确类型**（`type(x) is str`）。用 `isinstance` 时，子类（包括 `StrEnum`）能通过检查，等到事件或记录规范化时才失败，而这时状态可能已经改了。
  - 测试里用到较新的标准库特性（例如 3.11 才有的 `StrEnum`），要对照项目声明的最低 Python 版本给出回退。

## 4. 写合同

- task-id：小写字母、数字与连字符，不超过 64 个字符；版本从 v1 开始，每次返工加一。
- 以 [contract-template.md](contract-template.md) 为模板写 `.agent/plans/<task-id>.vN.md`，替换所有【待填…】。
- 机器合同优先用工具生成：`bash scripts/dispatch-pi.sh derive-json <task-id>.vN --title "<标题>"`。
  - 它按模板格式把 Identity、Scope、Validation commands、DoD 与 Budget 转写成同名 `.json`，写完立即校验。
  - 标题是一句短语，会成为 `branch` 生成的提交主题行 `<task-id>: <标题>`（标题已以 task-id 加冒号开头时不再重复）。不给 `--title` 时取 Goal 第一行，超过 60 字会提示。
  - 命令含复杂引号、或有 setup 需要额外字段时，参照 [contract-template.json](contract-template.json) 手工补充。
- **测试要求覆盖 Behavior contract 的每一条规则**，包括去重、排序、边界、键顺序这类细节；每条规则至少有一个用例能在它被改坏时失败。
  - 校验、权限、摘要或版本任务按 [test-design.md](test-design.md) 明确合法基线、唯一变化、具体错误和最小变异；防止另一条规则提前拒绝、非空分支缺失或多个字段同时变化掩盖缺口。
  - 实机例子：合同写了“按首次出现顺序去重”，测试清单里却没有重复词的用例。执行器照清单写测试，复审端的变异检查（review-pi 的 mutate）才发现这条规则无人把守。
  - 派遣前在草稿上逐条做最小变异，确认探针或测试清单能抓住。派遣后用 `mutate` 在候选上复核。
- **同一行为只写一次**：写在 Behavior contract 中，Steps、DoD 与测试要求引用它，不要换一种说法重写。两处说法不同时，执行器会自行选一种。
  - 实机例子：行为说明写“一条说明放在覆盖率条目的 note，另一条放在 notes 列表”，测试要求却写成“notes 中有两条说明”，执行器为此推敲了一轮。测试要求写成“见 Behavior contract 第 2 节”即可。
  - 检查行上的“基线应失败”是写给验收端的；执行器看到的机器合同摘要会把它写成“完成后必须通过”（调度工具 1.2.2 起）。
- **“某条 finding 由哪些模块产生”一类的事实要实测**：用小输入跑一次，列出所有来源。只读一个模块容易漏掉，例如解析器自己也会报同一规则。
- **设计代价公式、阈值一类的算法参数时，用参差的真实形态数据模拟**：只用等长、等间隔的例子，容易恰好掩盖公式的缺陷。实机上 v1 的对齐代价在等长对子上表现正确，时长不等时却仍把 80–91% 的 cue 揉进大组。先在副本上做原型，用独立复审的对照程序验证，再写进合同。
- 行号会随其他任务的集成漂移。Repository facts 引用代码时以函数、类等符号为主，行号只写“约 N 行”作辅助。
- **Repository facts 引用的上一轮合同、复审记录或设计说明（`.agent/` 下的文件）必须在基线里**。执行器的 worktree 按基线创建，读不到基线之后才提交的文件，也不得去主仓库读。
  - 侧分支基线常常不含这些文件，这时把需要的内容直接写进合同。
  - validate 会提示不在基线里的文件（调度工具 2.4.0 起）。
  - 实机：posix-identity-env v2 要求执行器读取 v1 合同与上一轮复审，两份都不在基线里。
- 用编辑工具写合同时，`\u200e` 这类转义序列可能被写成实际的不可见字符（Claude Code 的 Write / Edit 实测如此）。探针里需要这类字符时用 `chr(0x200E)`；validate 会对不可见格式字符给出警告。
- 字段含义、授权词表、检查与 DoD 的写法见 [contract-guide.md](contract-guide.md)。
- 执行模型默认用 Step 系列，`thinking: high`。provider 与 model 必须是本机 `pi --list-models step` 列出的精确 ID，并与 `.agent/environment.md` 一致。
- 参考示例：
  - 低风险：[examples/normalize-query.v1.md](examples/normalize-query.v1.md) 及其 `.json`
  - 高风险语义：[examples/auth-refresh-401.v1.md](examples/auth-refresh-401.v1.md) 及其 `.json`

## 5. 自检

1. 逐条回答 contract-guide.md 的“八个问题”。
2. 运行 `bash scripts/dispatch-pi.sh validate <task-id>.vN`。
3. 所有 ERROR 必须修正。WARN 要么修正，要么在合同里写明理由。
4. 修复类任务运行 `bash scripts/dispatch-pi.sh baseline <task-id>.vN`，确认用来证明修复的探针在基线上失败。
   - 这类探针在 JSON 中标 `"expect_on_base": "fail"`，Markdown 的检查行写“基线应失败”。
     - validate 比较两处标注（调度工具 2.4.0 起）：Markdown 写了而 JSON 不同是错误，只在 JSON 写了是警告。
     - 改了 Markdown 的标注后，用 `derive-json --force` 重新生成 JSON。
     - 实机：posix-identity-env v2 的 V06 在 Markdown 写了“基线应失败”，JSON 却是 any，baseline 根本没有核对它。
   - 在基线上就能通过的探针区分不了修复前后，要改写。
   - **只补测试、不改产品行为的任务**：基线上的产品代码本来就是对的，baseline 证明不了新测试有效。检查行按检查的形态写：
     - 只选中新增测试节点的检查（例如 `pytest tests/test_x.py::test_new`）：基线上收集不到用例，写“基线应失败”，并在合同中写明失败的原因是缺用例；
     - 运行已有测试文件或整个套件的检查，以及给已有测试补断言的任务：基线上照常通过，按回归保护写（`expect_on_base` 为 `pass`，或不写）；
     - 测试的有效性一律用变异证明：在 DoD 中列出必须抓住的最小变异（例如把被测的绝对路径改成相对路径），验收时用 review-pi 的 `mutate` 核对；
     - 实机：Codex 规划端的第一次试跑正是这类任务，4 个变异全部被新测试抓住。
   - baseline 只证明探针在基线上失败：第一条断言失败后，后面的断言根本没有运行。多段探针要在草稿修复上跑一次，确认能通过。做法是在临时 worktree 里做最小修改，运行探针与全量测试，同时确认只有合同点名的测试冲突；用完删除。

## 6. 交付

向用户报告：计划标识、一句话目标、范围、风险、验收项、预算，以及仍需用户决定的问题。

- 用户在本对话中已明确要求执行：继续用 dispatch-pi 派遣 `<task-id>.vN`。
- 否则停在这里，并说明派遣会把合同与相关代码发给执行模型提供商，并产生费用。

## 返工（上一轮结论为 REVISE）

新版本 vN+1 的输入是上一轮 REVIEW 与失败检查的关键输出。二选一，并在合同里写明：

- **从原基线重做**：base_sha 不变，写明放弃旧实现。
- **在上一轮候选上继续**：先运行 `bash scripts/dispatch-pi.sh branch <run-dir> --rework`，把输出的提交设为新 base_sha。
  - 如果集成分支在这期间已经前进（例如同批其他任务已经合入），可以先把返工提交重放到当前 HEAD 上：在临时 worktree 中 `git cherry-pick` 返工提交，给结果起一个分支名，再以它为 base_sha。
  - 这样新版本能看到已集成的改动，也能直接验证依赖它们的行为；通过后集成分支快进即可。

Steps 只写需要修正的差异，不要写“再试一次”。先查看 `bash scripts/dispatch-pi.sh status <task-id>`：attempt 次数和累计时长按 task-id 汇总，达到上限就不要再派遣，改为 ESCALATE。
