# 变异检查（mutate）

用途：确认新增测试真的能抓住合同规定的行为。做法是逐个把实现改坏一点，看测试会不会失败。
- 全部通过的测试不一定有效：用例可能恰好避开了某条规则，比如输入里没有重复项、传入的都是绝对路径。
- 执行器自述与 fresh 检查都看不出这一点。

## 何时做
- 中高风险任务的 G5 质量复审。
- 执行器写了大量新测试、复审者一时判断不了覆盖面时。
- 集成之后也可以补做：状态为 INTEGRATED 的 attempt 仍然可以运行。

## 命令

```bash
bash scripts/dispatch-pi.sh mutate <run-dir> --spec <清单.json> [--keep-workspace]
```

执行步骤：
1. 建干净副本：基线 + 候选补丁 + setup，与 `check --fresh` 相同。
2. **先不做变异，运行一次 command**。它必须通过，否则拒绝继续：命令本身不通过时，变异结果没有意义。
3. 逐个套用变异，运行 command，然后恢复原文件。判定：
   - 失败（退出码非 0 或超时）：**抓住**；
   - 通过：**漏掉**；
   - `old` 的出现次数与 `count` 不符：**跳过**，文件不改；
   - 命令无法启动：**出错**。
4. 记录写到 `<run-dir>/mutations/NN/`：
   - `mutations.json`：每个变异的结果、日志路径与汇总；
   - `spec.json`：清单副本；
   - `baseline.log` 与 `M01.log` 等每次运行的日志。
     - 日志按清单中的位置编号，与变异名称里自带的编号无关；命令输出的每行结果都写着位置编号与日志路径（调度工具 2.4.1 起）。
5. 执行 worktree 与候选都不受影响。

## 清单格式

```json
{
  "command": ["python", "-m", "pytest", "-q", "-p", "no:cacheprovider", "tests/test_jobs.py", "-k", "export"],
  "cwd": ".",
  "timeout_seconds": 600,
  "mutations": [
    {"name": "draft 取调用方参数", "file": "subtitle_qa/jobs.py",
     "old": "\"draft\": not passed_gate,", "new": "\"draft\": bool(draft),", "count": 2},
    {"name": "不去重", "file": "subtitle_qa/semantics.py",
     "old": "        if marker not in matched:\n            matched.append(marker)",
     "new": "        matched.append(marker)"}
  ]
}
```

- `command`：argv 数组，不经过 shell。只跑与改动相关的测试，缩短每轮时间。
- `old` / `new`：
  - 按 LF 书写即可。文件是 CRLF 时，工具先按 LF 比对，写回时再换回 CRLF。
  - `old` 必须恰好出现 `count` 次（缺省 1），全部替换。
  - 锚点选得太短，同一段文字会出现多次，这时要么写全上下文，要么写明 `count`。
  - 先用 `mutate --tree <树> --spec <清单> --check-anchors` 核对每条锚点的出现次数（调度工具 2.5.0 起），再跑变异；候选的注释行也可以进锚点（KitExperiment review-verdict：4 条因锚点在两个方法里各出现一次而跳过）。
  - `new` 包含完整的 `old` 时，原代码仍在，变异只是插入了新代码。插入的代码不改变被测行为时，结果必然是漏掉，却说明不了缺少测试。调度工具 2.4.2 起会在开头给出 WARN，并在结果行标“只插入代码”。顺序类变异要把计算真的挪走：例如“回收之前计算事实”要删掉回收之后的那次计算，不能只在前面多算一次。
  - 这个提示只看文字包含：`x if c else y`、`a or b`、在原语句前插入一次写入，都包含完整的 `old` 却改变了行为（KitExperiment ledger-reference 的三个 WARN 都被抓住）。按日志判断，不按提示判断。
- 用 Write 工具写清单时，`\u` 转义可能被写成实际字符（见 plan-task 第 4 节）。清单里需要这类字符时直接写字符本身。

## 多条命令与预期（2.8.0）

候选固定后通常要跑两轮：oracle 加执行器测试一轮，只用执行器测试一轮。2.8.0 起写进同一份清单，每条变异只套用一次、每条命令各跑一次：

```json
{
  "commands": [
    {"id": "all", "argv": ["python", "-m", "pytest", "-q", "-p", "no:cacheprovider", "tests/test_x_oracle.py", "tests/test_x.py"]},
    {"id": "executor", "argv": ["python", "-m", "pytest", "-q", "-p", "no:cacheprovider", "tests/test_x.py"]}
  ],
  "timeout_seconds": 600,
  "mutations": [
    {"name": "M01 跳过的原因改名", "file": "pkg/x.py", "old": "...", "new": "...", "expect_missed": ["executor"]},
    {"name": "M07 逻辑时钟自增", "file": "pkg/x.py", "old": "...", "new": "...", "equivalent": "自增的步长在输出里观察不到"}
  ]
}
```

- `commands` 与 `command` 只能写一个。`id` 写进日志文件名（`M01-all.log`、`baseline-executor.log`）和结果行的 `[all]`；每条命令可以有自己的 `cwd` 与 `timeout_seconds`，缺省用清单顶层的。
- `expect_missed`：这些命令预期漏掉。合同交给 oracle、没有列给执行器的规则标 `["executor"]`。
- `equivalent`：写明等价的理由，表示每条命令都预期漏掉；与 `expect_missed` 只能写一个。
- 结果行与汇总把预期与意外分开，例如 `executor：抓住 12，漏掉 20（预期 18，意外 2：M07 M14）`。只判意外的。标了预期漏掉却被抓住的也是意外：等价判断或“留给 oracle”的划分错了，复审记录里更正。
- `mutations.json` 每条结果的顶层是第一条命令的结果（单命令清单的形状不变），`commands` 里是每条命令的，`unexpected` 列出与预期不符的命令，`counts_by_command` 是每条命令的计数。退出码不变：意外只列出，不改退出码。
- 决策模型（2.6.0）只问意外漏掉的条目。
- `review-draft` 按这些标注写复审记录：意外漏掉的写成固定格式、归因留【待填】，等价的预填“等价变异”，`expect_missed` 的合并成一行“预期内”。

## 怎样选变异
- 先看合同 DoD 的“目的”子句（2.6.0）：每条目的至少一个变异。变异证明的是测试保住了目的，不是让检查变绿。
合同 Behavior contract 的**每一条规则各做一个最小变异**：
- 删掉一个条件：例如去掉版本核对、去掉去重；
- 放宽一个边界：例如词边界只看字母，`>=` 改成 `>`；
- 从常量里删掉一项；
- 调换写入顺序：例如先写文件再核验；
- 改一个输出字段：例如键缺失、布尔值取反；
- 吞掉一类错误：例如 OSError 之后返回 0。

不做语法破坏或大面积删除。那类改动任何测试都会失败，说明不了覆盖面。

自动生成字段故障时先确认锚点对应真正的声明，不能只按缩进和冒号猜字段；docstring里的`only:`曾被误识别，改动虽能编译却不影响行为。可用AST枚举声明，逐项确认目标。已经执行的纯文字故障保留原日志、从有效数剔除，不能计作执行器漏检。

保值故障要真的产生错误值。例如对象不可变时，直接给字段赋值只会触发`frozen_instance`，不能证明测试发现了字段丢失；应在同一返回点构造含错误值的合法副本。先核对故障到达目标输出，再看独立断言是否失败。输入协议要求特定异常类型时，变异导致未捕获的Python异常可以是有效的错误协议差异，与构造故障自身被不可变机制拦截分别判断。

对照 [测试设计](../plan-task/test-design.md) 选择能隔离规则的反例。比如去掉用途授权时，输入的状态必须允许该用途；去掉摘要中的非空对象字段时，测试必须真的有合法非空对象。类型相关规则要分别覆盖各类型，并用无关字段故意不同的正例防止错误收紧。

## 结果怎么处理
- 在复审报告的“范围与质量”中写：抓住 / 漏掉 / 跳过的数目，并逐个说明漏掉的变异。
- 工具的 **caught 只是命令没有通过**，包括超时。必须读日志，确认预期用例因为行为差异失败；语法、导入、收集错误、环境故障或单纯超时不算规则被有效保护，修正探针后再验证。原始计数不手改，人工有效性判断另记复审报告。
  - pytest 退出码为 2、日志里有 `!!! KeyboardInterrupt !!!` 时，是变异让中断冒出了测试，整个会话被打断，后面的用例都没有运行。这是测试缺陷：测试应当拦住冒出的中断，让失败只落在一个用例上。调度工具 2.3.0 起把这种情况记为出错（error），不计入抓住。
- 多次运行可能是追加少量探针，并非完整重跑。按 candidate_tree 与 spec 核对覆盖范围，汇总同一候选上的规则证据；不能只读编号最大的一轮，也不能将重复规则累加为新的覆盖。更正无效探针时保留原日志，标明替代关系。
- **漏掉**的变异说明没有测试覆盖那条规则。先判断原因：
  - **合同测试清单遗漏**：合同写了这条规则，测试要求里却没有对应用例。这是规划问题，不算执行错误。
    - 处理：由规划端补一条测试，确认它在实现上通过、在该变异上失败，集成后单独提交。
  - **执行器少写**：合同明确列出的用例没有写，或写了但断言太弱。
    - 处理：记入复审；影响结论时 REVISE。
  - **变异与原实现等价**：例如 `split()` 改成 `split(None)`。
    - 处理：不算缺口，在报告中注明。
    - 调度工具 2.6.0 起，决策模式开着时每条 MISSED 都问过决策模型“等价改写还是测试缺口”：`on` 模式下结果行带 `决策：可能等价 p=0.85` 一类后缀，shadow 只记在 `mutations.json` 每条的 `decision` 里。它决定先读哪条，不决定结论：判定仍是读代码（先问数据能不能区分，再判等价），复审记录写你的判定，`decisions replay` 时与它对照。
  - **测试的输入恰好观察不到差异**：例如输入全是绝对路径，而变异改的是相对路径的处理。
    - 处理：另用一次性探针实测该行为，把结果写进报告；需要长期保护时补测试。
- **跳过**多半是锚点写错了，修正清单后重跑，编号会递增。

## 在草稿上先跑一遍

规划端在派遣前用草稿验证 oracle 时，用同一种清单对草稿树跑 `mutate --tree`（调度工具 2.5.0 起；此前要另写临时脚本，KitExperiment 三轮反馈都点名要它）：

```bash
bash scripts/dispatch-pi.sh mutate --tree <草稿 worktree> --spec <清单.json> [--out <空目录>]
bash scripts/dispatch-pi.sh mutate --tree <草稿 worktree> --spec <清单.json> --check-anchors
```

- 判定与 attempt 模式是同一段代码：只有退出码非 0 或超时算抓住，会话中断记为出错，只插入代码的变异标出。规划端此前的临时脚本把任何非零退出码都算抓住，掩盖过一次会话中断（KitExperiment win-supervise）。
- 记录写到系统临时目录（结束时打印路径）或 `--out` 指定的空目录，不写进被变异的树；每条变异之后恢复原文件，结束时核对清单里的文件逐字节未变。
- `--check-anchors` 只核对每条 `old` 的出现次数，不运行命令、不写文件：候选固定后按候选措辞重锚时先跑它，`MISMATCH` 的锚点改好再跑变异。
  - 2.8.0 起不符时给出提示：出现 0 次，列出文件里最相近的至多 3 行（行号与原文）；出现多次，列出每一处的行号与锚点之后的下一行，补一行上下文就能唯一。
- 清单在派遣后原样交给 `mutate <run-dir>` 复核候选（锚点换成候选的写法）。
- 漏掉的变异先问数据能不能区分（字母序的种子分不出“排序”与“种子顺序”、单个请求分不出“忽略请求”），再判等价（KitExperiment task-done 两条草稿变异就是这样补的）。实机：pi-native-events 的草稿 32 个偏差全部抓住，漏掉的一个（空工具名）当场补进 oracle。

## 实机经验（KitExperiment）
- posix-supervisor a002：
  - oracle、探针与执行器测试合起来，30 个变异抓住 29 个。漏掉的是“轮询间隔改为 0.5 秒”：执行器拿每次休眠与模块常量比较，属于执行器少写，由规划端补测。
  - 独立复审另提出两个“中断后重置截止时间”的变异，追加运行后都漏掉了：规划端探针只断言了“没有提前结束”。规划端补了“没有延后”的用例。
  - 只用执行器测试时，“等待被中断后重新抛出”让 pytest 会话以退出码 2 中断，工具照样记为 caught。
- supervisor-stream-facts a001：
  - 37 个变异抓住 33 个。其中“回收之前计算事实”是规划端写错的变异：它在回收之前多算了一次，回收之后的计算还在，行为没有变化。
  - 按正确写法，这条顺序规则也没有测试能抓住。补测的做法是用 `mock.patch.object` 包装模块内部的 `_reap_group`：让回收一直等到组内成员写完。这样正确的实现总是通过，先算事实的实现几乎总会漏掉成员的写入。
  - 另外两个漏掉的变异（摘要读到 EOF、字节数取 `fstat` 的大小），只有在摘要期间文件变长或变短时才看得出来。补测时包装 `os.pread`，在第一次读取前改动文件。
- supervisor-stream-facts a002：
  - 32 个变异抓住 30 个。“上限在定义时绑定”又是规划端写错的变异：它只把上限挪进函数签名的默认值，函数体照旧读模块全局，行为不变。2.4.2 的提示抓不到这种情况，因为它并不是只插入代码。把签名与函数体一起改之后，这个变异被抓住。
  - “回收之前计算事实”漏掉，是因为规划端的顺序用例只是概率性的，改由测试自己发信号之后才确定（见 plan-task 的 test-design.md）。
  - 教训：变异写好之后，先确认它确实改变了一个可观察的结果（读一遍改后的代码，或者做一次性探针），再把“漏掉”算作测试缺口。
- durable-ledger a002：
  - 36 个变异抓住 34 个。“重放只接 `ContractError` 与 `TypeError`”对现在的调度器是等价写法：规划端与独立复审对 16 个变更方法伪造了一万多次参数，只得到成功或 `ContractError`。这条兜底规则防的是以后的调度器，用补丁让被调方法抛出 `KeyError` 之类来钉住，并断言错误码：变异体同样会关闭连接，只查描述符杀不死它。
  - 一条检查有两份时（两个函数里各一条规范检查；`O_EXCL` 之前的 `lstat` 预检），单独去掉任何一处都被另一处遮蔽，是规划端写错的变异。改它们共用的正则，或去掉更深的那一道，再用包装 `os.lstat` 的用例绕过前一道。
  - 规划端补全之后 41 个抓住 40 个：新加的通用分支吸收了“`RecursionError` 不单独映射”，它成了等价写法。

- task-done a001：29 条按候选措辞 27/29，锚点在候选上先用脚本逐条 `count` 核对（0 条跳过）。等价变异的两类：两条互斥状态之间的检查顺序（已接受的任务不可能有活动操作）；"最后一个"与"任意一个"在之后不可能再有元素时相同。草稿阶段两条变异一开始“漏掉”是 oracle 的数据不能区分（字母序 = 种子顺序、只有一个请求），不是实现等价——漏掉时先问数据能不能区分，再判等价。
- review-verdict a001：31 条按候选措辞 30/31；草稿阶段 4 条因锚点在 `fixture_verdict` 与 `verdict` 里各出现一次而跳过（`old 出现 2 次`），1 条因候选把一句条件拆成两句并加了注释而跳过——锚点要先 `grep -c` 确认唯一，候选的注释行也要进锚点。等价变异的又一类：对已释放的资源再释放一次（幂等的清理）。
- run-cli-pi a001：15 条两轮都 13/15；漏掉的一条是 oracle 盲点（子集用例恰好含被加上的维度），规划端补全改用例后单独跑那一条确认抓住。只插入死代码的变异（kit 标 WARN“只插入代码”）漏掉不算漏测，不要为它补测试。
- run-cli-recover a001：草稿与候选对新增命令的写法几乎相同（合同逐字给了调用行与 `register`），草稿锚点 14 条全部可用，按候选扩到 28 条后 27/28。等价变异的一类：把 `except X` 换成 `except Y`，而 X 是 Y 的子类（`RuntimeErrorCode(ValueError)`）——判定前查类层次，不要补测试。
- run-cli-once a001：草稿锚点的 29 条里 20 条 SKIPPED，只剩 9 条可用；按候选措辞重写 37 条后 36/37（漏掉的 1 条等价）。结论：候选固定后先读 diff，按候选的写法写变异清单，草稿锚点那轮只当预演，不要拿它的抓住数下结论。
- win-wiring a001：第 1 轮 25 条里 5 条 SKIPPED——锚点写在规划端草稿的措辞上，执行器用 `if/return` 代替条件表达式、改了错误消息文本；按候选措辞重锚补跑一轮（6/7），漏掉的 1 条是 oracle 缺口（几千位的文本身份让 `int()` 抛 ValueError 而不是被拒绝），规划端补用例后单独重跑确认抓住。只用执行器测试 6/20，漏掉的全是清单留给 oracle 的规则。SKIPPED 不是漏测也不是抓住，必须重锚再下结论。
- win-supervise a001：32 个变异，oracle 加执行器测试 31/32，剩下 1 条“出错”而不是漏掉：变异体让回收轮询里的 `KeyboardInterrupt` 逃出去，pytest 整个会话被打断（退出码 2），不算抓住。断言“中断被吸收”的 oracle 用例要自己 `try/except KeyboardInterrupt` 再 `self.fail`，规划端补全后单独重跑这条变异确认抓住。只用执行器测试 16/32，漏掉的 16 条全是清单留给 oracle 的规则（平台守卫、挂起与入 Job 的顺序、退出码数值、子进程环境与 cwd、启动失败的形状、`KILL_ON_JOB_CLOSE`）。

- ledger-reference a001：
